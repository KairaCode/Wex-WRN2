# scripts/

**Current.** Build and check scripts that exist only in this repository. They used to sit among the mirrored files; `c/` now holds only the engine-side WEX files.

- `check_all.sh`: every check of this repository that needs no GPU, no model and no engine tree, in one command: `check_repo.py` (self-test and check), three standard-library tests (`scripts/test_verify_wex1.py`, `c/tests/test_repack_v4_wex.py`, `c/tests/test_build_nr3_picks.py`), `build_cpu_check.sh`, `wex4/build_and_test.sh`, then `wex4/research/fast-cpu-decode/synth.sh check` (the fast WNR3 decoder's own harness on 4 synthetic records: its SIMD build and its scalar build against the reference decoder). Run `bash scripts/check_all.sh` from anywhere; last line on success: `all checks passed`. It is what the CI jobs `linux`, `linux-arm`, `macos`, `windows` and `linux-sanitizers` run, followed by `bash wex4/fuzz/run.sh --replay`; the three Linux ones then also run the smoke mode of `bench/wex_io.py` (see [`../bench/README.md`](../bench/README.md)), which this script does not build or run. `CC` names the C compiler of the three scripts that build C (`build_cpu_check.sh`, `wex4/build_and_test.sh`, `synth.sh`; each prints one `compiler:` line; default `gcc`; the `macos` CI job sets a Homebrew GNU gcc there, because the `gcc` of Xcode is Apple clang, without OpenMP; CI also runs the whole check with `CC=clang` on Linux, in the `linux-tsan` job, which fails unless the three `compiler:` lines name a clang; no other compiler was run through `CC`, and the scripts pass their gcc flags, `-fopenmp` among them, as they are). `CC` is also read by `wex4/fuzz/run.sh --replay`, `sanitize_c.sh`, `bench/wex_io.py`, `build.sh` and `negative_control.sh` of `wex4/research/fast-cpu-decode/` and `wex4/research/vulkan-decode/run.sh`. It is not read by the older research scripts that no check runs (`wex4/research/fast-cpu-decode/verify/run.sh`, `wex4/research/mxfp4-contexts/run_all.sh`, the two scripts of `wex4/research/wnr4-record/`) or by `integration/build/build_test_wex_planned.sh`: they call `gcc` by name. `WEX_CFLAGS` adds flags to every compiler call of those three scripts; the `linux-sanitizers` CI job puts its sanitizer flags there and preloads the ASan runtime, because the tests load the libraries into Python (the exact flags and options are in `.github/workflows/ci.yml`).
- `sanitize_c.sh`: the C test executables, and the libraries that the Python tests load, under ThreadSanitizer or MemorySanitizer, `bash scripts/sanitize_c.sh tsan` or `bash scripts/sanitize_c.sh msan`; last line on success: `tsan run passed` or `msan run passed`. Linux with clang only (the MSYS2 clang has neither sanitizer); `tsan` also needs the OpenMP runtime of that clang with its Archer tool (Ubuntu: `libomp-N-dev`). It first builds two controls: a file with a deliberate data race or a read of an uninitialised byte, which the sanitizer must report, and for `tsan` a correct OpenMP loop, which must give no report. Then it runs `c/tests/test_wex_format.c` (`msan` only), `c/tests/test_wex4_verify.c`, `c/tools/wex4_verify.c` over the valid conformance vectors and a WEX4 file of 4 synthetic WNR3 records (on 8 threads under `tsan`, on one under `msan`), and the five harnesses of `wex4/fuzz/` on their seeds (`wex4/fuzz/run.sh --replay`), then `fuzz_wex4_file` and `fuzz_wnr3_record` on that file, where a record has 192 weight streams, which the fast decoder splits into 4 OpenMP tasks; the script prints these two numbers and stops if there are fewer than 2 tasks. `tsan` builds with `-fopenmp`, `msan` without it, so under `msan` the OpenMP loops run on one thread. Then the three libraries that the Python tests load through ctypes (`wex4/wex4_tools.c` with the fast and with the reference WNR3 decoder, `c/tools/wex_nr3_tools.c`, the WNR3 encoder), built as `wex4/build_and_test.sh` builds them with the sanitizer added, are loaded and called by `sanitize_libs.c` (next item), after a control library with a deliberate data race and a read of an uninitialised byte, loaded the same way, has been reported. Under `tsan` only, `wex4/build_and_test.sh --fuzz 100` (`wex4/test_wex4.py` and `c/tools/build_nr3.py`) then runs with its three libraries built under ThreadSanitizer and the shared ThreadSanitizer runtime of the clang preloaded into every Python process, with `libgcc_s`, which that runtime needs to print a crash; each process writes its reports to a file of `out/tsan/py-reports/`, and one file fails the run. Two controls go through Python first: the deliberate race must be reported and the correct OpenMP loop (one call on the main thread, then 4 threads at once) must not. No such run exists for `msan`: the clang 18 of ubuntu-24.04 has no shared MemorySanitizer runtime, and Python, which is not instrumented, writes the buffers it passes to the libraries, which MemorySanitizer would take for bytes nobody wrote. A `tsan` log also names the Archer library in use. Seen while this was set up, not in the code of this repository (clang 18.1.3 and libomp 18 on ubuntu-24.04 runners, GitHub Actions runs 43715100673 and 43715660316): with Archer, a correct OpenMP loop with a `critical` section that 4 threads start for the first time at once crashed inside the OpenMP runtime (a read at address 0x1a0 in `__kmpc_end_critical`) in 4 of 6 runs of a C program, and from Python in 6 of 8 runs without `libgcc_s` preloaded (exit status 127, the report lost: the runtime found no `_Unwind_Backtrace`) and in 4 of 8 with it (the report printed). Without Archer, from Python, it did not crash in 6 runs, but each run gave 3 false reports, the kind that Archer removes; with one call on the main thread first it ran clean 6 times of 6, in C and in Python. The WEX4 tests and `sanitize_libs.c` start the runtime on the main thread first. It is what the `linux-tsan` and `linux-msan` CI jobs run (clang 18 on ubuntu-24.04, x86-64); no report from either, on the executables on 2026-11-14 and on the libraries on 2026-11-15. In GitHub Actions run 43716610833 (one run) the two library steps took 84 s of the `tsan` run, 70 s of them the WEX4 tests, and 24 s of the `msan` run; the job `linux-tsan` took 3 min 41 s and `linux-msan` 1 min 39 s, against 2 min 33 s and 1 min 7 s in run 43670519543 of `main` before these steps. Output goes to `out/tsan/`, `out/msan/`, `wex4/fuzz/out/` and, for `tsan`, `wex4/out/` (git-ignored).
- `sanitize_libs.c`: the C program of `sanitize_c.sh` that stands in for Python. It loads `wex4_tools.dll` (fast and reference WNR3 decoder) and `wex_nr3_tools.dll` as ctypes does (`dlopen` with `RTLD_LOCAL`; `LoadLibrary` on Windows) and calls every function they export, with the inputs of `wex4/test_wex4.py`, `wex4/wex4.py`, `wex4/wex4_convert.py` and `c/tools/build_nr3.py`: SHA-256 on 203 lengths and 3 known answers; 288 WBP1 records encoded by both libraries (the same bytes), decoded by both and refused for another owner; every row of `wex4/vectors/MANIFEST.tsv` (verdict, error class, SHA-256, root) and the synthetic WEX4 file through `wex4_check` and `wex4_fuzz_check`; `wex4_validate`, `wex4_decode_record_buf` and `wex4_expert_table` on the accepted files; `wex4_store_probe` on the three files with an expert grid (a wrong root, a table over budget and a flipped record bit refused); `wex4_fuzz_run` in its 3 modes on 3 files, 18 calls on 4 threads at once (4,823 mutations through each library in `sanitize_c.sh`); the WNM2 model trained and the 4 synthetic experts encoded, verified and decoded on 4 threads, with and without canonical zero, the model and the records byte-identical to those `build_nr3.py` wrote; those records decoded through both decoders back to the source slabs. Output buffers that a function must fill are left uninitialised, so that MemorySanitizer reports a byte the library did not write. `sanitize_libs --control LIB` is the control of `sanitize_c.sh`. Usage and the eight parts are in its header; last line on success: `sanitize_libs: all checks passed`. Not covered: the Python code paths themselves (that is the `tsan` run of the WEX4 tests above), and other inputs than these. Besides clang on Linux it was built and run with MSYS2 gcc 16.2 on Windows, without a sanitizer and not in CI.
- `build_cpu_check.sh`: the CPU self-test of `c/`, no GPU and no real model. It builds and runs `c/tests/test_wex_format.c` and `c/tests/test_wex4_verify.c` (the WEX4 checker `c/tools/wex4_verify.c` on small synthetic WEX4 files: an intact file passes with the expected root, changed records, padding, blobs, index and header page fail; it prints one summary line), compiles `c/tools/wex4_verify.c` alone, compiles the WNR3 encoder DLL and the CPU stand-in helper, then builds a WEX1, WNR3-CZ bins and a WNR3-CZ container from `fixtures/v41-tiny`. Run `bash scripts/build_cpu_check.sh` from the repository root with MSYS2 UCRT64 or MINGW64 `gcc` on `PATH`; last line on success: `WNR3 CPU check passed`. The summary line `"gate_failures": 144` above it is not an error: it counts the matrices (48 records x 3) of the tiny fixture on which ceil-form was not used. Output goes to `out/cpu-check/` (git-ignored). With a colibri engine `c/` folder (one that holds `expert_store_registry.c` and the engine headers) as first argument it also builds and runs `c/tests/test_expert_store_wex.c`, which needs engine headers.
- `verify_wex1.py`: byte check of a WEX1 / WEX2 / WEX3 container against the safetensors checkpoint it was built from: `python -I scripts/verify_wex1.py --model-dir DIR --wex FILE [--stride N]`. It rejects a WNR2 container (check that with `archive/nr2/check_container.c` or `archive/nr2/check_all.py`); WNR3 and WEX4 are outside its scope (for WEX4: `python -I wex4/wex4.py verify FILE`).
- `test_verify_wex1.py`: its test on a synthetic model, `python -I scripts/test_verify_wex1.py`.

The repository check, [`../check_repo.py`](../check_repo.py), is at the root. The GPU builds are in [`../integration/build/`](../integration/README.md); the WEX4 tests are run by [`../wex4/build_and_test.sh`](../wex4/README.md).
