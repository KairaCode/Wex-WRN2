# scripts/

**Current.** Build and check scripts that exist only in this repository. They used to sit among the mirrored files; `c/` now holds only the engine-side WEX files.

- `check_all.sh`: every check of this repository that needs no GPU, no model and no engine tree, in one command: `check_repo.py` (self-test and check), three standard-library tests (`scripts/test_verify_wex1.py`, `c/tests/test_repack_v4_wex.py`, `c/tests/test_build_nr3_picks.py`), `build_cpu_check.sh`, `wex4/build_and_test.sh`, then `wex4/research/fast-cpu-decode/synth.sh check` (the fast WNR3 decoder's own harness on 4 synthetic records: its SIMD build and its scalar build against the reference decoder). Run `bash scripts/check_all.sh` from anywhere; last line on success: `all checks passed`. It is what the CI jobs `linux`, `linux-arm`, `macos`, `macos-clang`, `windows`, `linux-sanitizers` and `linux-arm-sanitizers` run, followed by `bash wex4/fuzz/run.sh --replay`; the four Linux ones then also run the smoke mode of `bench/wex_io.py` (see [`../bench/README.md`](../bench/README.md)), which this script does not build or run. `CC` names the C compiler of the three scripts that build C (`build_cpu_check.sh`, `wex4/build_and_test.sh`, `synth.sh`; each prints one `compiler:` line; default `gcc`; the `macos` CI job sets a Homebrew GNU gcc there, because the `gcc` of Xcode is Apple clang, which refuses `-fopenmp` and has no OpenMP runtime; CI also runs the whole check with `CC=clang` on Linux, in the `linux-tsan` job, which fails unless the three `compiler:` lines name a clang, and with Apple clang on macOS, in the `macos-clang` job, which fails unless they name Apple clang; no other compiler was run through `CC`, and the scripts pass their other gcc flags as they are). `WEX_OPENMP` replaces the OpenMP flag of those three scripts (default `-fopenmp`; `wex4/fuzz/run.sh` builds without OpenMP). For Apple clang it names the `libomp` of Homebrew: with `P=$(brew --prefix libomp)`, `WEX_OPENMP="-Xclang -fopenmp -I$P/include -L$P/lib -lomp -Wno-unused-command-line-argument"`, the line of the `macos-clang` job (the last flag keeps the compile-only and preprocessor calls from warning that `-L` and `-lomp` are not used). `CC` is also read by `wex4/fuzz/run.sh --replay`, `sanitize_c.sh`, `bench/wex_io.py`, `build.sh` and `negative_control.sh` of `wex4/research/fast-cpu-decode/` and `run.sh` and `bench.sh` of `wex4/research/vulkan-decode/`. `build.sh` and `negative_control.sh` read `CC` but not `WEX_OPENMP`: they pass `-fopenmp` as it is, which Apple clang refuses, so they cannot build with it (neither was run with Apple clang; `build.sh` also passes `-march=haswell` and is x86 only). It is not read by the older research scripts that no check runs (`wex4/research/fast-cpu-decode/verify/run.sh`, `wex4/research/mxfp4-contexts/run_all.sh`, the two scripts of `wex4/research/wnr4-record/`) or by `integration/build/build_test_wex_planned.sh`: they call `gcc` by name, and they were left so on 2026-11-15 because none of them can run without inputs that are not in this repository (records or the container of the real DeepSeek V4.1 model, its checkpoint, numpy, or an engine tree in the maintainer's layout), so a change could not be run to its end. `WEX_CFLAGS` adds flags to every compiler call of those three scripts; the `linux-sanitizers` and `linux-arm-sanitizers` CI jobs put their sanitizer flags there and preload the ASan runtime, because the tests load the libraries into Python; `macos-clang` does the same on macOS, where the runtime is put into the interpreter with `DYLD_INSERT_LIBRARIES` through a two-line script named in `PYTHON` (the exact flags and options are in `.github/workflows/ci.yml`).
- `sanitize_c.sh`: the C test executables under ThreadSanitizer or MemorySanitizer, `bash scripts/sanitize_c.sh tsan` or `bash scripts/sanitize_c.sh msan`; last line on success: `tsan run passed` or `msan run passed`. Linux with clang only (the MSYS2 clang has neither sanitizer); `tsan` also needs the OpenMP runtime of that clang with its Archer tool (Ubuntu: `libomp-N-dev`). It first builds two controls: a file with a deliberate data race or a read of an uninitialised byte, which the sanitizer must report, and for `tsan` a correct OpenMP loop, which must give no report. Then it runs `c/tests/test_wex_format.c` (`msan` only), `c/tests/test_wex4_verify.c`, `c/tools/wex4_verify.c` over the valid conformance vectors and a WEX4 file of 4 synthetic WNR3 records (on 8 threads under `tsan`, on one under `msan`), and the six harnesses of `wex4/fuzz/` on their seeds (`wex4/fuzz/run.sh --replay`; one of them, `fuzz_wnr3_cuda`, is the CUDA WNR3 decoder built as C++ for the CPU, with the clang++ that goes with `CC`), then `fuzz_wex4_file` and `fuzz_wnr3_record` on that file, where a record has 192 weight streams, which the fast decoder splits into 4 OpenMP tasks; the script prints these two numbers and stops if there are fewer than 2 tasks. `tsan` builds with `-fopenmp`, `msan` without it, so under `msan` everything runs on one thread. A `tsan` log also names the Archer library in use. Not covered: the libraries that the other checks load into Python, because both sanitizers need the whole process instrumented. It is what the `linux-tsan` and `linux-msan` CI jobs run (clang 18 on ubuntu-24.04, x86-64); no report from either on 2026-11-14, nor on 2026-11-15 with `fuzz_wnr3_cuda` among the harnesses (runs [43716852459](https://github.com/KairaCode/Wex-WRN2/actions/runs/43716852459) and [43769078721](https://github.com/KairaCode/Wex-WRN2/actions/runs/43769078721)). Output goes to `out/tsan/`, `out/msan/` and `wex4/fuzz/out/` (git-ignored).
- `build_cpu_check.sh`: the CPU self-test of `c/`, no GPU and no real model. It builds and runs `c/tests/test_wex_format.c` and `c/tests/test_wex4_verify.c` (the WEX4 checker `c/tools/wex4_verify.c` on small synthetic WEX4 files: an intact file passes with the expected root, changed records, padding, blobs, index and header page fail; it prints one summary line), compiles `c/tools/wex4_verify.c` alone, compiles the WNR3 encoder DLL and the CPU stand-in helper, then builds a WEX1, WNR3-CZ bins and a WNR3-CZ container from `fixtures/v41-tiny`. Run `bash scripts/build_cpu_check.sh` from the repository root with MSYS2 UCRT64 or MINGW64 `gcc` on `PATH`; last line on success: `WNR3 CPU check passed`. The summary line `"gate_failures": 144` above it is not an error: it counts the matrices (48 records x 3) of the tiny fixture on which ceil-form was not used. Output goes to `out/cpu-check/` (git-ignored). With a colibri engine `c/` folder (one that holds `expert_store_registry.c` and the engine headers) as first argument it also builds and runs `c/tests/test_expert_store_wex.c`, which needs engine headers.
- `verify_wex1.py`: byte check of a WEX1 / WEX2 / WEX3 container against the safetensors checkpoint it was built from: `python -I scripts/verify_wex1.py --model-dir DIR --wex FILE [--stride N]`. It rejects a WNR2 container (check that with `archive/nr2/check_container.c` or `archive/nr2/check_all.py`); WNR3 and WEX4 are outside its scope (for WEX4: `python -I wex4/wex4.py verify FILE`).
- `test_verify_wex1.py`: its test on a synthetic model, `python -I scripts/test_verify_wex1.py`.

The repository check, [`../check_repo.py`](../check_repo.py), is at the root. The GPU builds are in [`../integration/build/`](../integration/README.md); the WEX4 tests are run by [`../wex4/build_and_test.sh`](../wex4/README.md).
