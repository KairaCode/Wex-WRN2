# WNR3 compressed-record RAM cache with size classes, 2026-11-10

**Verdict: no speed gain at equal RAM, not adopted.** The code stays on KAIRA branch `wnr3-ramcache-20261110` (commit 25922b2, `deepseek_v4.c` and `tests/test_v4_wex_nr3.c`), not merged into master and not copied into this repo. Production context: [docs/WNR3-PRODUCTION-20261110.md](../../../docs/reports/WNR3-PRODUCTION-20261110.md).

Paths `lab\...` and `app\...` are relative to the KAIRA tree (`<KAIRA>`); the run folders stay there.

## What the cache does

`COLI_WEX_RAM_CACHE_GB` keeps WNR3 records **compressed** in page-locked host RAM, exactly as stored in the container, and decodes them on the GPU on a hit (same GPU-direct decode as a disk read, without the read). A WNR3 record averages 0.854 of a WEX1 slab, so the same RAM holds more experts than decoded slabs do. Prefill does not use the record cache; it serves decode only.

## Design: size classes

The first version gave every slot the size of the largest record, so a GiB held `budget / max_record` records. The new version:

- splits the container's record sizes into **equal-count quantile classes** (`COLI_WEX_RAM_CACHE_CLASSES`, default 8, range 1..16; 1 = the old max-size slots);
- sizes each class's slot to the largest record in that class, and gives each class slots in proportion to its share of the records;
- lays all slots out in one pinned arena;
- on a claim takes the smallest class that fits the record, evicts LRU inside that class, and spills to a larger class when the class is all leased;
- prewarms coldest first, so a full class evicts its colder records; open logs a capacity line, the end-of-run report adds `classes=` and `fill_eff=`.

With the cache unset the engine is unchanged.

On the real V4.1 REAP-192 WNR3 container (record sizes min 15.25, median 15.30, mean 15.31, max 16.61 MiB), one RAM step of **752,025,600 B** (one decoded slab per layer: 40 x 18,800,640 B = 0.7004 GiB) holds:

| layout | records in 0.7004 GiB |
|---|---|
| decoded slabs | 40 |
| compressed records, max-size slots | 43 |
| **compressed records, 8 size classes** | **46** (+15% vs slabs), fill efficiency 0.991 |

## Equal-RAM rule

The cache must not get RAM the baseline does not have. Arm B gives up one decoded slab per layer and puts exactly those bytes into the record cache:

- A: plan default, 8 decoded slots per layer (`target_slots=8`), no record cache.
- B: `COLI_V4_EXPERT_SLOTS=7` + `COLI_WEX_RAM_CACHE_GB=0.7004`, `COLI_WEX_RAM_CACHE_CLASSES=8`.

## Result

| measure | A (8 slabs) | B (7 slabs + 0.7004 GiB records) | B vs A |
|---|---|---|---|
| decode, arm mean | 3.038 tok/s | 3.032 tok/s | **-0.19% ± 0.72%** (paired, n=14 run x prompt) |
| TTFT | 8.05 s | 8.09 s | +0.36% ± 2.04% |
| wait per token | 121.6 ms | 124.4 ms | +2.8 ± 2.2 ms |
| token ids and logits | | | identical in every run, logits bit-identical |

Same-arm spread between runs: 0.49% (A), 0.80% (B).

Record cache counters (B1 / B2): 46 slots, 8 classes 15.28-16.61 MiB; prewarmed 38 / 40; **hits 50 / 52, misses 60,556 / 61,157**; GPU-direct decode failures 0.

## Why it does not help

The decode routing touches far more distinct experts than 46 records: about 61,000 lookups per run and 52 hits. In total the cache holds 6 more experts than the 40 slabs it replaces, which is not enough to change the hit rate measurably; the arms differ by less than their noise. Together with the Windows memory-compression measurement (production doc, RAM section), neither OS compression nor the compressed record cache gives a speed gain at this RAM budget.
