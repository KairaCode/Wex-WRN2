## Why it fits the containers unchanged

Quark's MXFP4 expert tensors have the same byte layout as V4.1's: FP4 E2M1 nibbles in U8 plus one E8M0 scale per 32 weights. Only the names differ (`gate_proj` / `up_proj` / `down_proj`, scales as U8). So one expert is one WEX1 record of the V4.1 kind, and the WNR3 encoder takes it as input with no change to the codec. Quark emits no FP4 -0, so canonical zero gives nothing here.

Checks:
- **WEX1 repack** (`repack_q38_mxfp4_wex.py`, 4 min). Every one of the 512 records on layers 0 and 47 is byte-identical to the Quark tensors. Against FP8 on all 48 layers, min cosine is 0.9926 and relative error is 0.115-0.122, which confirms nibble order and scales.
- **WNR3 build** (`build_nr3.py --layers all --train-lab80`, 471 s, 24,576 records, 0 raw fallbacks). Layers 0, 10, 23 and 47 decode to the WEX1 records bit for bit on the GPU, at 1.5-1.6 GB/s per record and 1.9-2.0 GB/s in batches of 10.

## Speed

One run per arm. Each run is a fresh `coli serve` with KAIRA's qwen38 profile (MTP off, prompt lookup on), RAM 13 GB, RTX 5090. Raw records: `research/qwen38-mxfp4-20261111/speed-*.json`.

| decode tok/s | FP8 | MXFP4 WEX1, U: only | MXFP4 WNR3, U: only | MXFP4 WEX1, U:+C: 38/62 (installed) |
|---|---|---|---|---|
| 258-token prompt, 200 tokens | 4.39 | 11.48 | 9.48 | **12.45** |
| 2k-token prompt, 30 tokens | 3.07 | 7.18 | 5.27 | **7.44** |
| 3-turn chat | 2.2-2.4 | 5.2-5.5 | 3.8-4.1 | **5.8-6.2** |
| TTFT, 2k prompt | 94.5 s | 64.9 s | 76.5 s | **62.2 s** |

- **MXFP4 against FP8:** 2.3-2.6x faster in decode. A record is 2,613,248 B against 4,915,200 B for an FP8 expert, and about 25.5 GB of experts fit in VRAM.
- **WNR3 against WEX1:** without a mirror, WNR3 is 17-30% slower than WEX1 on one drive. The 12% smaller reads do not pay for the GPU decode. This is the same pattern as V4.1 before its mirror.
- **WEX1 with the mirror:** +3% to +13% over one drive (one run each). An ABBA has not been run.
- **Outputs:** the generated text is identical across the WEX1, WNR3 and mirror runs.

## After the install: engine-side gains (2026-11-11 evening)

Raw records, scripts and the WEX4 move log: [`research/qwen38-speed-20261111/`](../../research/qwen38-speed-20261111/README.md).

All runs: WEX1 on U: with the C: mirror (38/62), RAM 13 GB, RTX 5090, fresh `coli serve` per arm.

**VRAM arena (`QT_ARENA=1`), installed.** The expert tier gives each MXFP4 expert a slot of its exact size instead of a padded one. By the research's count the tier then holds 9,049 experts instead of 7,178 at the same charged budget. One ABBA, identical texts:

| decode tok/s | A (`QT_ARENA=0`) | B (`QT_ARENA=1`) | gain |
|---|---|---|---|
| 258-token prompt | 12.93 / 13.26 | 15.52 / 14.49 | +14.6% |
| 2k-token prompt | 7.17 / 8.67 | 10.50 / 9.50 | +26.3% |
| 3-turn chat | 4.6-7.1 | 7.7-8.5 | +23% to +44% |

The two A runs differ from each other, so the size of the gain is less certain than its sign.

**Prefix store for the system prompt, installed.** The upstream prefix store is ported to qwen38 (KAIRA 951facd). In one control run it held up to 1089 MiB and reused 65-75% of later turns' prompts.

**Two CPU-side fixes, installed** (KAIRA 99ccadc, in e245f4c):
- **Sampler.** At temperature above 0, `qwen38.c` ran a full `qsort` of the 248,320-entry vocabulary on every token, about 24 ms per token standalone. It now samples through `qwen36_sample.h`, which sorts only the nucleus.
- **One OpenMP team for expert reads.** `q38_read_team()` in `qwen38_core.h` runs every expert read wave on the matmuls' OpenMP team. A team sized to the record count makes libgomp restart pool threads: on the old code a 2-record wave restarted 14 threads (check in `<KAIRA>/src/colibri/c/tests/test_qwen38_native_weights.c`).

One A/B pair at temperature 0.6 with `QT_ARENA=1`, the new build run first. The text is identical in all 5 requests.

| decode tok/s, temperature 0.6 | A (951facd build) | B (e245f4c) | gain |
|---|---|---|---|
| 258-token prompt | 12.54 | 18.02 | +43.7% |
| 2k-token prompt | 7.80 | 10.85 | +39.1% |
| 3-turn chat | 5.90 / 6.30 / 6.35 | 8.83 / 8.85 / 8.94 | +40% to +50% |

The pair was not repeated. TTFT is about equal in both arms (10.2 / 10.5 s on the 258-token prompt, 49.5 / 47.0 s on the 2k prompt, A / B). The sampler gain exists only at temperature above 0; KAIRA sends 0.6.

**The container format is speed-neutral here** (research of 2026-11-11 from code, logs and CPU microbenches, with no engine run):
- WEX4 around the same raw records: 0%.
- WNR3 as the read format: -19% to -29%.
- Decode is bound by the experts that are not resident in VRAM and are computed on the CPU. Of 80.3 ms per token on the 258-token prompt, the disk is about 16 ms.

So the Qwen3.8 containers keep raw records, also inside WEX4.

WEX4 for the real qwen38 containers: done on 2026-11-11 at 23:18-23:24. Both WEX1 copies were upgraded in place with `wex4_convert.py upgrade FILE --names qwen38`, the C: mirror first: 64,224,956,416 B -> 64,251,047,936 B each (+26,091,520 B, index 26,086,592 B, 24,576 records, records left RAW), same root `db5389f699abb49a164a9e73d925b5b629b0ce6de430a553388ba3e1cae5c0df` on both. ## How KAIRA runs it

The MXFP4 engine sits in its own directory, `app\colibri-q38mx` (`qwen38.exe`, `coli_cuda.dll`, `kaira_wex_cuda.dll`), and the profile also sets `QT_ARENA=1`. Nothing in `app\colibri-optimized` changed, so the DeepSeek and qwen36-family engines keep their own DLLs. The `qwen38` profile adds:

```
COLI_ENGINE=<KAIRA>\app\colibri-q38mx\qwen38.exe
COLI_WEX_PATH=U:\kaira_wex\qwen38-mxfp4\q38_experts.wex
COLI_WEX_EXTRA_MIRRORS=C:\kaira_wex\qwen38-mxfp4
COLI_WEX_WEIGHTS=38,62
```

`COLI_WEX_EXTRA_MIRRORS` names a directory; the engine opens the same file name there and accepts it only if the header page and entry table are byte-identical. The C: copy's SHA-256 equals U:'s (`a2d0f67f...`). The engine logs `WEX mirror active` and `2 drive(s) split 38% 62%`.

An independent read of the host and launcher code confirmed:
- KAIRA passes all four variables through unchanged.
- `coli` honours `COLI_ENGINE` for this family.
- Nothing checks for the old exe in `runtime_dir`.

## Open points

- **MTP + MXFP4 is untested.** KAIRA's global MTP switch is off today and overrides the profile's `Q38_MTP=1`. If it is turned on, the MTP head runs its experts from FP8 on the CPU, next to the MXFP4 layers. The code keeps the two apart, but no test or real run covers the combination.
- **RAM budget.** The measurements ran at RAM 13 GB. KAIRA derives the budget from available memory, which is about 20 GB on a quiet machine. The engine has its own load gate and commit cap.
- **Mirror split.** 38/62 is V4.1's split on the same two drives and has not been tuned for Qwen.
- **Engine-side results need repeats.** The arena ABBA and the sampler / read-team pair were each run once.
- **Output line.** `qwen38.c` prints the generated text on the same line as the `C engine :` ids (a missing newline). The harness works around it.
