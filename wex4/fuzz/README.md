# wex4/fuzz/

**Current.** Coverage-guided fuzzing harnesses for the C readers and decoders, for [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (and AFL++ through its libFuzzer driver). They complement the in-process mutation fuzzer of [`../wex4_tools.c`](../wex4_tools.c) (`wex4_fuzz_run`, run by [`../build_and_test.sh`](../build_and_test.sh)): that one applies a fixed number of random edits to three files on every run of the tests; these keep the inputs that reach new code and can run for hours.

| Harness | Input | Code under test | What must hold, besides the sanitizers |
|---|---|---|---|
| `fuzz_wex4_file.c` | a whole WEX4 file | `c/wex4.h`: header page, index, RAW / WBP1 / WNR3 record decoding, through `check_impl` of `wex4_tools.c` | each input is checked as it is (every hash verified) and again with the header and index hashes recomputed and the records decoded without their hash, so that a mutation reaches the validators and the decoders. A file accepted with its hashes decodes to the same content digest without them; decoding twice gives the same digest; a file whose records decode has a header page and an index that validate |
| `fuzz_wnr3_record.c` | the stored bytes of one WNR3 record | `wex_nrx_parse` and `wex_nr2_decode` (`c/wex_neural_rans.h`), `wex_fast_decode` (`../research/fast-cpu-decode/wex_fast_decode.h`) | the reference and the fast decoder give the same verdict, and on success the same bytes. The model and the layout come from the first WNR3 record of a real container (`WEX_FUZZ_BASE`, default `wex4/vectors/valid/tiny2-cz-upgraded.wex4`); the input is zero-padded to a multiple of 4096 bytes, up to that record's decoded size rounded up to 4096 |
| `fuzz_wex4_verify.c` | a whole WEX4 file | `c/tools/wex4_verify.c` (through a temporary file: the checker takes a path) | it answers "does not open as WEX4" exactly when `wex4_parse_header` or `wex4_open` refuses the same bytes, and the root of a file it passes is the SHA-256 of bytes [0, 4064) |
| `fuzz_store_wex.c` | a whole legacy container (WEX1, WEX2, WEX3) | `c/expert_store_wex.c` opened without an engine, with `c/wex_decode.c` and `c/wex_format.h` (through a temporary file named by `COLI_WEX_PATH`): open, lookup, release, prefetch, statistics, close; in a second pass (`store_paths.h`) the mirror of `COLI_MODEL_MIRROR`, the read split of `COLI_DISK_WEIGHTS`, `WEX_READ_RETRY` and `DSV4_CUDA_MOE_MASKED`; in a third pass the same with reads that fail (`read_faults.h`) | the store opens the file exactly when `wex_validate_header`, `wex_validate_table` and the model checks accept the same bytes in memory; a lookup succeeds exactly when the record's bytes pass the owner check and decode with `wex_decode_record` or `wex_decode_nr2_record`, and the three matrices it hands out are those decoded bytes; an expert that loaded loads again, and a cache hit reads no byte; the request, hit and miss counters add up. In the second pass: the store opens exactly when a mirror copy it takes has the input's size, header page and table (and refuses a canonical-zero container under `DSV4_CUDA_MOE_MASKED=1`), and every expert is read from the file the split names. In the third pass: an open with one of its reads failed fails; a prefetch whose read failed publishes nothing; a lookup whose read failed returns no record unless `WEX_READ_RETRY=1` read it again without a failure, and then it gives the record's verdict; the lookup after a failed one gives the record's verdict and bytes |
| `fuzz_q38_wex.c` | a whole container (WEX1, legacy WNR3, WEX4) | the container reader of the Qwen3.8 engine, `c/qwen38_wex.h`: `q38_wex_manifest`, `q38_wex4_manifest`, `q38_wex_entry_ok`, the model registration, `q38_expert_mx4_attach`, `q38_mx4_load` (a WEX4 file twice, without and with `COLI_WEX_VERIFY=1`); in a second pass (`q38_paths.h`) the mirrors of `COLI_WEX_EXTRA_MIRRORS`, the read split of `COLI_WEX_WEIGHTS`, the striped read of `COLI_WEX_STRIPE` and, with a CUDA helper, the load wave (`q38_mx4_decode_wave`); in a third pass reads that fail (`read_faults.h`) and the root pin of `COLI_WEX_ROOT` | the attach does not stop on a container whose manifest, entries and model the same functions accepted; every record of an attached container lies inside the file and its read fits its slab; a load stops the engine exactly when the record fails the first-read hash (when it is on), the owner check or `wex_decode_nr2_record`, and otherwise the slot holds exactly the decoded bytes. In the second pass: the attach takes, in order and at most three, exactly the mirror copies that differ from the input in record bytes only; the split's cuts are the weights' shares of 256; every load reads the drives the split names (a striped read cut on a page by the two drives' shares) and stops exactly when the bytes so read fail the same checks; a load wave stops exactly when one of its records does not decode. In the third pass: the manifest refuses a container when one of its reads fails, and a failed read of the model stops the engine; the manifest takes a WEX4 file under its own root (in any case) and refuses it under another, and refuses a legacy file under any root; a load whose read failed (either half of a striped read) stops the engine, and the load after it gives the record's verdict and bytes |
| `fuzz_wnr3_cuda.cpp` (C++) | the stored bytes of one WNR3 record (as `fuzz_wnr3_record`), or a whole WEX4 file, of which every WNR3 record is decoded with its own entry and model | the CUDA WNR3 decoder built for the CPU ([below](#the-cuda-decoder-on-the-cpu)): the kernels of `c/wex_cuda.cuh` and the four decode calls of `c/tools/wex_cuda_bridge.cu` (`wex_cuda_decode_to_host`, `_to_device`, `_batch_to_device`, `_batch_to_host`), on two builds, and the kernels alone with both weight lookups; with `run.sh --gpu`, the same kernels also on an NVIDIA GPU ([below](#the-same-kernels-on-a-gpu)) | every path returns 0 exactly when `wex_decode_nr2_record` accepts the record, and then gives its bytes; otherwise -1, or 1 when the record names a model that is not registered. A refused record leaves the destination of the four calls untouched (of the batch to host since 2026-11-17, when that call went to rounds that copy back only the records that decoded clean; before, it was the first three). The valid record next to it in a batch decodes, in either order. The error word holds no bit but 1, 2, 4 and 8, bit 8 only under the CZ flag and bit 4 only under a CEIL flag |

## The two engine harnesses

`c/expert_store_wex.c` and `c/qwen38_wex.h` are engine files: they include headers that are not in this repository, and their own tests (`c/tests/test_expert_store_wex.c`, `c/tests/test_qwen38_mxfp4.c`) build only inside an engine tree. The harnesses build them here against the stand-ins of [`engine/`](engine/):

The stand-ins were compared on 2026-11-15 with [colibri](https://github.com/JustVugg/colibri) `dev` at commit `98327913f980514970173b6df7bf67210ad0dc16` (2026-11-15), and, for the Qwen3.8 types, with the open colibri pull request #2825 (commit `5e0a0b5`, MXFP4 experts read from a sidecar). Each declaration cites the colibri file and line it follows.

- `engine/expert_store.h`, `engine/deepseek_v4_internal.h` and `engine/compat.h` stand for the engine headers of those names and for the `tensor.h`, `deepseek_v4.h` and `expert_store_registry.h` they include. Every type, member and enumerator the store uses has colibri's name, type and order. `engine/compat.h` declares nothing: the store uses nothing of colibri's `compat.h`. The harness defines the two engine functions the store calls: `coli_v4_expert_store_open_planned` (it opens nothing; colibri's opens the RAM-tiered store of an engine) and `coli_expert_store_backend_register` (it records nothing).
- `engine/q38_engine.h` declares the engine types `c/qwen38_wex.h` names. What `c/qwen38_wex.h` takes from colibri's `compat.h` and `st.h` is copied, with its line. That includes `compat_open_direct`, which `c/qwen38_wex.h` calls on macOS, where there is no `O_DIRECT`: it opens the file read-only and sets `F_NOCACHE` (colibri `c/compat.h:59-63`; issue #22). The configuration, the weight, the slot, the model and the expert index have colibri's types and order for every member colibri has. Inferred, because no public tree has them: the members `c/qwen38_wex.h` adds to the expert index (`mx`, `mx_*`, `wex_*`), the weight's `e8` (pull request #2825 holds the same bytes in a member named `x2q`), the value of `Q38_WEIGHT_MXFP4` (10, as in #2825) and `q38_slab_unpin`. A difference between these and the engine's types is one this harness cannot see. No public colibri tree includes `c/qwen38_wex.h`, so it cannot be built inside colibri itself.
- What the comparison found in the stand-ins of 2026-11-14: `ColiTensorFormat` lacked its last three formats (`INT8_BLOCK`, `INT4_BLOCK`, `GGML`; the value of the one the store uses, `COLI_TENSOR_FP4_NATIVE_BLOCK`, was right); `ColiDeepSeekV4Config` was an incomplete struct where colibri has a complete typedef; `engine/compat.h` defined `Sleep` outside Windows, which colibri's `compat.h` does not, so the store did not build against colibri on Linux or macOS (it now has its own pause for `WEX_READ_RETRY`, `wex_retry_pause` in `c/expert_store_wex.c`); `st_tensor` had another member order, 4 dimensions where colibri has 8 and no `name` or `numel`; `Q38WeightKind` was `{F32 = 0, MXFP4}` where colibri starts with `NONE = 0` and has 10 kinds before MXFP4; `Q38Weight`, `Slot` and `Model` had their members in another order or lacked some; `q38_weight_free` and `q38_name` did nothing like colibri's; the Windows read of the stand-in had no event in its `OVERLAPPED` and made one read where colibri's loops over pieces below 2 GiB, and its last-error variable was not per thread. The stand-in `compat_open_direct` did what colibri's does. The replay passes with the stand-ins of both dates.
- `WEX_FUZZ_COLIBRI=fetch bash wex4/fuzz/run.sh --replay` (or `WEX_FUZZ_COLIBRI=<a colibri checkout>`) builds the two harnesses a second time against colibri's own headers in place of the stand-ins and replays their seeds (for `fuzz_q38_wex`: colibri's `compat.h` and `st.h`; its model types stay those of `engine/q38_engine.h`, checked against `qwen38_core.h` by reading, not by `engine_layout.c`). It also builds `engine_layout.c` against both: the program prints the offset, size and signedness of every member and the value of every enumerator of the declarations above, and the replay fails unless the two listings are equal. `fetch` takes the `c/*.h` of the pinned commit (`COLIBRI_COMMIT` in `run.sh`) with git into `out/colibri`; nothing of colibri is copied into this repository (colibri is under the Apache License 2.0, like this one). The listing does not cover the model types of `engine/q38_engine.h`, which no public colibri header declares in the form `c/qwen38_wex.h` needs, nor what a function does. The folder that `fetch` leaves, `out/colibri/c`, also holds colibri's `expert_store_registry.c`, so `bash scripts/build_cpu_check.sh wex4/fuzz/out/colibri/c` builds and runs the store's own test, `c/tests/test_expert_store_wex.c`, against colibri's files. Run on 2026-11-15, once each: on Windows 10 (MSYS2 UCRT64 gcc 16.2, against the same commit from a local clone: the replay and the store's test), and in the opt-in `colibri-headers` job of CI on Linux (ubuntu-24.04, gcc 13.3) and macOS (macos-15, Homebrew gcc 15.3), run [43768999583](https://github.com/KairaCode/Wex-WRN2/actions/runs/43768999583) of commit `1d1874e`: the 81 lines of `engine_layout.c` agreed, both harnesses replayed their seeds against colibri's headers, and the store's test passed. On macOS the Qwen3.8 harness built this way opens its files with colibri's own `compat_open_direct`. gcc 15.3 on macOS printed one `-Wformat-truncation` warning in colibri's `st.h` (line 713), none in this repository's files. Later on 2026-11-15 colibri `dev` was at `1a06018699d5ca18040797e31ad4b7baf12260a2`, 33 commits on, with none of the nine files the stand-ins cite changed (`tensor.h`, `expert_store.h`, `deepseek_v4.h`, `deepseek_v4_internal.h`, `expert_store_registry.h`, `expert_store_registry.c`, `compat.h`, `st.h`, `qwen38_core.h`; `git diff` between the two commits), and pull request #2825 was still open at `5e0a0b5`. The replay against that commit's headers and the store's test against its files passed too (Windows 10, MSYS2 UCRT64 gcc 16.2, once, `WEX_FUZZ_COLIBRI` naming a sparse checkout of it); the pin in `run.sh` stays at `98327913`.
- The engine stops with `exit(1)` on a container it refuses. In `fuzz_q38_wex.c` an `exit` inside `c/qwen38_wex.h` returns to the harness (`longjmp`), which first runs the same checks without the exit and calls the real attach only on a container that passed them. The geometry (layers, experts, hidden and intermediate size) is taken from the input, where the engine takes it from the model's configuration.
- Both harnesses empty the model registry of `c/wex_decode.c` (16 models for the life of the process) before every input, and send the log lines of the code under test nowhere.
- Both make a second pass over every container that opened, through the read paths the first pass leaves alone (`store_paths.h`, `q38_paths.h`, with what they share in `engine_paths.h`). A mirror is a copy of the input in a directory of its own, in one of six forms: the same bytes, one byte changed in every page of every record, one byte changed in the header page or in the table (or the WEX4 index), a page appended, no file; or the input's own directory. The form says whether the code under test must take the copy, and a copy whose records differ shows a read from the wrong drive, or a striped read cut at the wrong page. Which form, weights and switches an input gets depends on its bytes only, so a crash file replays the same way. Each new check was broken once on purpose, in a copy of the harness (ten edits of what the harness expects. Qwen3.8: the drive, the stripe off, the stripe cut at the middle page, the weights, the copies taken, the first-read hash, the decode of a wave, with the stand-in helper. Store: the drive, the cut, the bytes compared); each edit made the replay of the seeds fail (2026-11-15, Windows, gcc 16.2, once each; the scripts of that check are not in the repository).
- Both then make a third pass, with reads that fail. `read_faults.h`, included right before the engine file, sends that file's reads through two wrappers (`pread`; on Windows `ReadFile`, and `pread` where the engine's `compat.h` defines it as `compat_pread`) that let a given number of reads through and fail the next one or two, as an I/O error. A pass first counts the reads of a clean call, then fails one of them. The store is opened with one of its reads failed (header page, table, model, the mirror's header page and table), an expert is prefetched with its read failed, then looked up with its read failed, with `WEX_READ_RETRY` off, or on with one read failed (so the second read succeeds) or two. For `c/qwen38_wex.h` the harness calls `q38_wex_manifest` and `q38_wex_model` itself with one read failed, and `q38_wex_manifest` under `COLI_WEX_ROOT` set to the WEX4 file's own root (in capitals for one input in 2), to that root with one digit changed, and, for a legacy file, to a root of zeros; then it loads one expert alone with one of its reads failed (either half of a striped read). A refused manifest is checked by calling it, not the attach: there the engine exits, holding a page, a table and a descriptor that the harness, which goes on, would leak. The checks were broken on purpose in copies of the engine files, nine edits of the code under test, each in its own copy (store: a failed read not seen; no second read under `WEX_READ_RETRY`; the second read not checked; a prefetch that publishes a failed load. Qwen3.8: a failed read not seen by `q38_wex_read`; a load that ignores a failed read; a striped read that ignores its second half, Windows code; the root pin ignored on WEX4; on a legacy file). Each made the replay of the seeds stop with a failed oracle, the prefetch one with an oracle of the second pass, which runs first (2026-11-15, Windows 10, MSYS2 UCRT64 gcc 16.2, once each; the script of that check is not in the repository). In one `--replay` (the seeds and the mutator's inputs made from them; Windows 10, gcc 16.2, 2026-11-15) the pass of the store refused 262 opens with a failed read and made 262 lookups with a failed read, 28 of them read again and served; that of Qwen3.8 refused 106 manifests, stopped 22 model reads and 106 loads (41 of them striped), and took 33 root pins and refused 106.

Every line of `c/expert_store_wex.c`, `c/qwen38_wex.h`, `c/wex_decode.c`, `c/wex_format.h` and `c/wex4.h` that the harnesses run is the real one.

## The CUDA decoder on the CPU

`fuzz_wnr3_cuda.cpp` runs the CUDA source of the WNR3 decoder without a GPU and without the CUDA toolkit. What a run proves is the decoding logic of the kernels and the order of the bridge's CUDA calls. It does not prove that nvcc compiles the same thing, that a GPU runs it the same way, or anything about speed; the GPU test is `c/tests/test_wex_nr3_gpu.cu` (nvcc and a GPU, run by hand).

- `cuda_host.py` writes a host C++ copy of `c/wex_cuda.cuh` and `c/tools/wex_cuda_bridge.cu` to `out/wex_cuda_host/`. It rewrites what a macro cannot reach, each by an exact pattern whose number of matches it checks: the 13 kernel launches `<<<...>>>`, the 4 `__shared__` declarations, the 3 inline PTX statements (`prmt`, `cp.async`, its commit and wait) and the `cuda_runtime.h` include. The bridge is copied unchanged. When `c/` changes so that a pattern no longer matches, the script stops.
- `cuda_host.h` emulates the rest; its header comment lists every construct. The blocks of a grid run one after the other, in a random order. The threads of a block that reaches `__syncthreads()` run at the same time, one host thread each, and the barrier is a real one; the threads of the other kernels run one after the other. Shared and device memory are filled with 0xA5, so that a read of a byte nothing wrote gives a wrong byte. A 4-byte `cp.async` writes 0x9E3779B9 to its destination at once and the word arrives only at the `cp.async.wait_group` that covers it. `prmt`, `__byte_perm`, `__funnelshift_l`, `__popc`, `__vmaxu2`, `__vminu2` and the atomics compute what the CUDA documentation says. Copies, kernels and events are queued per stream and run when the host waits; the next operation is drawn at random among the streams that may run, so a missing wait between two streams gives wrong bytes. A launch is checked as the runtime checks it, and every pointer passed to a kernel must come from `cudaMalloc`.
- Not emulated: warp-level operations (the kernels have none), a warp in lockstep, two blocks at the same time, an operation that overlaps another one (a copy or a kernel runs whole), the GPU's memory model, the legacy default stream, several devices, timing. The copies are compiled by g++ or clang++, with `__CUDA_ARCH__` defined for the host code too, which does not test it.
- The source is built twice in the harness, as nvcc builds it for two targets: `sm86` (`__CUDA_ARCH__` 860 and the weight lookup 1, the bridge's default; the scale table in shared memory and the payload ring filled by `cp.async`; a device of compute 8.6 with 99 KiB of shared memory per block) and `sm75` (750 and lookup 0: the table in global memory, the ring filled by loads, the bucket lookup; 7.5 with 64 KiB).
- At start it decodes 15 records that no vector has: a synthetic expert (497, 315 and 495 scales, two of its three matrices in ceil form) with and without canonical zero at the chunk pairs 512:256, 1024:512 and 16384:16384; a record at 14 bits per symbol, the highest load of the payload ring; and eight records that only one check refuses: a byte after the end of a stream, an initial state below L, an initial state at 256 L or above (each in a scale and in a weight stream), a -0 under the CZ flag, a block in ceil form at coded scale 0.
- `cuda_negative.py` is its negative control: 23 copies of the CUDA source, each with one check, one wait or one barrier removed or changed (the list is in the script), and the replay must fail on every one. Run it after `run.sh --replay`; the `linux` job of `.github/workflows/ci.yml` does. On 2026-11-17 the control "the copy back of the host batch does not wait for the kernels", whose text the new rounds of `wex_cuda_decode_batch_to_host` no longer have, became "the host batch copies back a record refused on the device" (the old behaviour, which the harness now refuses); all 23 failed on Linux (Ubuntu g++ 13.3, x86-64, one run), and the harness built on the bridge of before that change failed on the seeds with "wrote the destination of a record it refused". On 2026-11-15 all 23 failed, on Windows 10 (MSYS2 UCRT64 g++ 16.2, one run) and in CI ([43716852459](https://github.com/KairaCode/Wex-WRN2/actions/runs/43716852459) on commit `6b242f8` and [43769078721](https://github.com/KairaCode/Wex-WRN2/actions/runs/43769078721) on `3173368`, ubuntu-24.04, g++ 13.3).
- In that CI run the replay of `fuzz_wnr3_cuda` gave the same counts (585 inputs, 591 records, 263 accepted, no failed oracle) on x86-64 and ARM64 Linux, macOS (Homebrew g++ 15.3), Windows, under AddressSanitizer and UndefinedBehaviorSanitizer, and under ThreadSanitizer and MemorySanitizer (clang++ 18.1.3, through `scripts/sanitize_c.sh`), which reported nothing. The threads of a block of the scale kernel and of the weight kernel with lookup 1 (the kernels with a barrier) run as real threads, so ThreadSanitizer would report a race between them on shared or device memory; the threads of the other kernels, the weight kernel with lookup 0 among them, run one after the other and cannot race.
- Under libFuzzer it is slow: each input costs 12 emulated decodes under the sanitizers. In the Fuzz workflow on 2026-11-15 ([43717913457](https://github.com/KairaCode/Wex-WRN2/actions/runs/43717913457), ubuntu-24.04, 60 s, one run) it ran 421 inputs (430 records, 209 accepted by every path, 177 different decoded records, 31 refused on the device), where `fuzz_wnr3_record` ran 15,168 in the same run; its `cov` / `ft` were 6,924 / 25,456, which count the emulation and the C++ library too and cannot be compared with the other harnesses. On the last commit of that day ([43769081058](https://github.com/KairaCode/Wex-WRN2/actions/runs/43769081058), same conditions, one run) it ran 256 inputs (272 records, 127 accepted by every path, 93 different decoded records, 17 refused on the device). Two runs say little about the spread. A run of 60 s is a smoke test of this harness. The first such run ([43716855086](https://github.com/KairaCode/Wex-WRN2/actions/runs/43716855086)) stopped at its end on a LeakSanitizer report, 384 bytes in 24 allocations: the emulation's `cudaEventDestroy` kept every event. That was a fault of the emulation, fixed the same day; it said nothing about the decoder.

## The same kernels on a GPU

`bash wex4/fuzz/run.sh --gpu [ROUNDS]` runs `fuzz_wnr3_cuda` as `--replay` does, with ROUNDS inputs of the custom mutator per seed (default 4), and decodes every record whose plan the host accepts also on an NVIDIA GPU, with the kernels of `c/wex_cuda.cuh` unchanged. It needs the GPU's driver and clang with its NVPTX target (`CUDA_CLANG` names it), not the CUDA toolkit. Nothing of it runs in CI, which has no GPU; the `linux` job only builds it (`WEX_FUZZ_GPU_BUILD_ONLY=1`).

- `cuda_device.cu` and `cuda_device.h` let clang compile `c/wex_cuda.cuh` in its CUDA mode without the toolkit (`--cuda-device-only -nocudainc -nocudalib`) to PTX, once for `sm_86` and once for `sm_75`: the code for `__CUDA_ARCH__` 860 and 750, as in the emulation. `cuda_device.h` says what it defines and how (the qualifiers, `__ldg`, `__byte_perm`, `__funnelshift_l`, `__vmaxu2`, `__vminu2`, `__popc`, the two atomics, the conversion to a shared address); the inline PTX of the kernels goes through unchanged. The driver compiles the PTX for the GPU when the harness loads it.
- `cuda_gpu.h` opens the driver library (`nvcuda.dll`, `libcuda.so.1`) and calls the part of the CUDA driver API it declares. For each record, on each of the two modules: the kernels alone with both weight lookups, and the order of the bridge's `wex_cuda_nr2_decode` with its commit kernel on two streams, the record in page-locked memory, so that the copy of the weight payload runs while the scale kernel runs, as in the bridge. The oracles are those of the emulated kernels: the verdict of `wex_decode_nr2_record`, its bytes, no error bit but 1, 2, 4 and 8 (8 only under CZ, 4 only under a CEIL flag), and the commit's destination untouched when the record is refused. At start a kernel reports the layout of the structures the host passes by value, which must be the host's.
- What it does not run: nvcc (the production helper is built by nvcc; here clang's NVPTX back end and the driver's JIT compile the same source, and the code nvcc makes was not compared), the bridge's own code and the CUDA runtime it calls (`cuda_gpu.h` has its own copy of the bridge's sequence), `compute-sanitizer` (it comes with the toolkit), coverage guidance, a GPU below compute capability 8.0 (the `sm_75` PTX ran on the GPU there was) and any second GPU.
- `cuda_negative.py --gpu` puts each of its 20 controls on `c/wex_cuda.cuh` into the PTX instead of the host copy; the three controls of the bridge do not apply. The three that remove a barrier or shorten the `cp.async` wait are reported and not required: on a GPU they leave a race that may or may not change a byte.
- On 2026-11-15, one run of `run.sh --gpu 100` (NVIDIA GeForce RTX 3070, compute capability 8.6, driver API 13050, Windows 10, clang 23.1.5 for the PTX, MSYS2 g++ 16.2): 11,817 inputs, of which 7,906 WNR3 records had a plan the host accepts and a registered model and went to the GPU, 47,436 GPU decodes, 35,238 accepted with the CPU's bytes and 12,198 refused with the CPU; no failed oracle. It took 512 s of wall time while other builds ran on the machine (not a measurement). `cuda_negative.py --gpu` on the same machine: 17 of the 20 controls noticed, every one that is not a race; the two missing barriers and the short `cp.async` wait were not noticed there (a block is one warp, and on this GPU its lanes may still run together; a copy may land before its wait). The logs are in [research/cuda-review-20261115](../../research/cuda-review-20261115/README.md).

The review of this decoder against WNR3-SPEC and the runs of 2026-11-15 are in [research/cuda-review-20261115](../../research/cuda-review-20261115/README.md).

## The custom mutators and the dictionary

A WNR3 stream starts at a state that holds a 23-bit hash of the bytes it decodes to, and the decoder requires that state at its end. A byte changed in a stored record fails the first stream it touches, so with libFuzzer's own mutations the fuzzer reaches the decode loops and nothing behind an accepted stream. `wnr3_mutator.h` mutates on the other side of the codec: it decodes the record, edits the decoded scales and weights and the record's parameters (chunk sizes, owner, anchors, flags), and encodes the result with the reference encoder, which writes the right hash into every stream. Two calls in three it encodes the canonical way (canonical zero, ceil form); one in three it draws the flag bits at random, so that a record with right hashes is still refused later (a -0 under the canonical-zero flag, a scale of 0 in a block the ceil inverse has to undo).

`legacy_mutator.h` does the same for the older record codecs, in `fuzz_store_wex`. What a changed byte does to each of them, and what the mutation does instead:

- Scale tiles (codec 1) and palette (codec 2): the scales are a tile stream (per 256 scales a base, a bit width and the packed differences) that must end exactly at its stored length, so a changed width usually refuses the record. The mutation unpacks the scales, edits a few and packs them again, one tile in four with a wider width and a lower base that decode to the same values. In a palette record it also changes a few bytes of the three tables and of the packed 3-bit weights, which have no check: every value decodes.
- WNR (codec 3): the record holds its own model (a class per scale value, 17 CDFs of 16 symbols per class) and one rANS stream per 256, 512 or 1024 weights, which must end at its length with the state back at 2^23, so a changed payload byte almost always refuses the record. The mutation decodes it, edits weights, scales, the class of a scale value (to another class, or one time in 8 to none), a CDF row, the chunk size and the scale-only flag, and encodes it again. A scale value that an edit brings in and that has no class gets one 7 times in 8. No tool of this repository encodes WNR records on the CPU (`c/tools/wex_neural_rans.py` calls a CUDA library), so the encoder, `fuzz_wnr1_encode`, is written in `legacy_mutator.h` from the decoder `wex_nr_decode_weights` of `c/wex_neural_rans.h`.
- WNR2 (codec 4): the streams of WNR3 without the hash, the flags and the owner, with the same end condition. `wnr3_mutator.h` edits it as it edits a WNR3 record and encodes it with the reference encoder; its three medians are recomputed, or one time in 8 drawn at random (any value decodes).

A record is replaced in place only when the new one takes the same pages and is not the same bytes; a record that two entries share (WEX3 deduplication) changes for both. A structured call decodes the record first, so a record that the decoder refuses is not mutated again by structured calls, only by libFuzzer's own mutations.

Some WNR edits make a record that the decoder refuses, on purpose: a scale value left without a class (the encoder codes it with class 0 and the decoder stops at it), or the scale-only flag set over CDF rows that differ (the parser refuses it). The exit line of `fuzz_store_wex` counts, by codec, the replaced records that the store's checks refuse. A test program that is not in the repository called `fuzz_legacy_mutate` 20,000 times for each seed of `seeds/legacy/` and `seeds/engine/`, each time on a fresh copy of the seed, and decoded each rewritten record (Windows 10, MSYS2 UCRT64 gcc 16.2, run once). Of the WNR records it rewrote, 9.8% were refused in the seed with a context model (1,812 of 18,402: 887 with the scale-only flag over rows that differ, 925 with a scale without a class) and 5.5% in the seed with a scale-only model (861 of 15,621: 5 and 856). No refused WNR record had another cause: none failed in a rANS stream. Every palette (19,998), WNR2 (18,560) and scale-tile (19,999) record it rewrote was accepted. WNR3 records, rewritten by `wnr3_mutator.h` with flag bits drawn at random one time in three, were refused 29.6% of the time (5,896 of 19,918).

## Running them

```sh
bash wex4/fuzz/run.sh            # 60 s per run
bash wex4/fuzz/run.sh 14400      # 4 hours per run
bash wex4/fuzz/run.sh --replay   # no fuzzing: gcc, every seed once through every harness
bash wex4/fuzz/run.sh --gpu 100  # fuzz_wnr3_cuda only, 100 mutator inputs per seed, the kernels also on an NVIDIA GPU
```

There are seven runs: one per harness (six), and a second run of `fuzz_store_wex`, named `fuzz_store_wex-legacy`, on the containers of the older codecs (`seeds/legacy/`) with a corpus of its own. The first run of `fuzz_store_wex` starts from the engine seeds alone, so the older codecs do not take the time of its WNR3 records (see the measurements above).

The first two need `clang` with libFuzzer, AddressSanitizer and UndefinedBehaviorSanitizer (`-fsanitize=fuzzer,address,undefined`): on Linux they are the compiler-rt runtimes (Debian and Ubuntu: `libclang-rt-N-dev`, which `clang` installs unless recommended packages are turned off; Fedora: `compiler-rt`); the MSYS2 UCRT64 clang does not accept `-fsanitize=fuzzer`, so on Windows use WSL or only `--replay`. Apple clang ships no libFuzzer runtime: on macOS name the clang of a Homebrew LLVM (`CC=$(brew --prefix llvm@18)/bin/clang`, which brings libFuzzer and both sanitizers; the Fuzz workflow takes the highest `llvm@N` of the runner image). That line was not run on a Mac of your own: CI used the `llvm@18` already on the runner image, and neither `brew install llvm@18` nor the step of the workflow that runs `brew install llvm` when the image has no `llvm@N` has run. `CC` names the compiler (`CC=clang-18`), `PYTHON` the interpreter (`PYTHON=python3` on Linux and macOS), as in the other scripts. `--replay` needs only `gcc` and `g++` (or the compiler named in `CC`, for example a Homebrew `gcc-15` or Apple clang on macOS, and the C++ compiler of the same name, `g++-15` or `clang++`, which `CXX` can name instead): it builds each harness with `-DWEX_FUZZ_STANDALONE`, which adds a `main` that runs the files named on its command line, and runs the seeds through it. A harness with a custom mutator also runs that mutator on every seed in `--replay` (200 inputs from each seed of `fuzz_wnr3_record`, 100 for `fuzz_store_wex`, 40 for `fuzz_wex4_file` and `fuzz_q38_wex`, 4 for `fuzz_wnr3_cuda`, whose inputs each go through 12 emulated decodes), with a small deterministic stand-in for `LLVMFuzzerMutate`: the mutator and the oracles behind it are tested without clang. On Windows `--replay` then runs `fuzz_store_wex` and `fuzz_q38_wex` a second time with a CUDA helper: the CPU stand-in `c/tests/fake_wex_cuda.c`, built as a DLL and named by `WEX_FUZZ_CUDA_LIB` (`c/wex_decode.c` loads a helper on Windows only). That run fails unless records were decoded through the helper. `WEX_FUZZ_COLIBRI` (above) adds the build against colibri's headers. Seven jobs of `.github/workflows/ci.yml` run `--replay` after the CPU checks: gcc on x86-64 Linux, on 64-bit ARM Linux and on macOS (Apple silicon, a Homebrew GNU gcc), on Windows, and under AddressSanitizer and UndefinedBehaviorSanitizer on x86-64 Linux and on 64-bit ARM Linux (`linux-sanitizers`, `linux-arm-sanitizers`); and Apple clang on macOS, once as it is and once under both sanitizers (`macos-clang`). `--replay` prints the compiler and the kernel of the fast decoder it built, and every ARM64 job fails unless it is NEON. One `--replay` took 28 s on 2026-11-14 (Windows 10 desktop, MSYS2 UCRT64 gcc 16.2, one run), 28 s again on 2026-11-15 with the seeds of the older codecs and the build of `legacy_seeds`, and 33 s with the WNR seeds written by `repack_v4_wex.py` and the second store run (same machine and compiler, one run each); with `fuzz_wnr3_cuda`, before the seeds of the older codecs, it took 93 s on 2026-11-15 (Windows 10 Pro, 8 logical CPUs, the same compiler, while other builds ran on the machine, one run: not a measurement). With the second and third passes of the engine harnesses and the runs with the helper, before the older codecs and `fuzz_wnr3_cuda` were merged, the replay step of the `windows` CI job took 21 s (windows-2022 runner, run 43768999583 of commit `1d1874e`, once, with the pauses of `WEX_READ_RETRY` still taken).

The seeds are the conformance vectors ([`../vectors/`](../vectors/README.md)): every file of the manifest for the two WEX4 file harnesses, and the WNR3 records of the accepted ones for the record harness (`make_seeds.py`). The two engine harnesses get nine small expert containers that `make_seeds.py` writes: a WEX1 file and a WEX2 file made there, the legacy vector `tiny2-cz.wex3`, the same with its grid cut to its two experts, the WEX4 form of two of them, and the WEX1 file twice more with the slab size of its header changed (twice its record, which is the most the validators accept, and 4 GiB - 4096, which they refuse), and a WEX1 file of 1 x 4 experts whose records are four pages long (so that a striped read is cut by its drives' shares, not only at its one-page minimum); `fuzz_q38_wex` also gets every file of the manifest. `fuzz_wnr3_cuda` gets the seeds of both WEX4 harnesses, and the four files of [`impl/go-wex4/testdata`](../../impl/go-wex4/testdata/README.md), whose `ceil-form.wex4` holds two WNR3 records with a CEIL flag besides those of the vectors. The run `fuzz_store_wex-legacy` gets, in their place, four WEX3 containers of the older codecs (`seeds/legacy/`; the Qwen3.8 reader takes none of them). Each holds one layer of the same four MXFP4 experts, which `make_seeds.py` makes (hidden and intermediate size 128, a slab of 28,672 bytes; the fourth is a copy of the first, and the third has a scale of 255 in each of its three matrices):

| Container | Written by | Records |
|---|---|---|
| palette, 86,016 B | `c/tools/repack_v4_wex.py` (format 3, `palette3`, any error allowed), from a safetensors checkpoint of the four experts | 2 palette, 1 raw (the writer does not quantize an expert with a scale of 255), 1 alias |
| WNR with a context model, 86,016 B | `repack_v4_wex.py` (format 3, `neural-rans`, chunks of 512 symbols), from the same checkpoint, with `legacy_seeds` in place of its CUDA encoder | 2 WNR, 1 raw (the model has no class for 255, so the writer does not code that expert), 1 alias |
| WNR with a scale-only model, 86,016 B | the same, chunks of 1024 symbols | 2 WNR, scale-only, 1 raw, 1 alias |
| WNR2, 131,072 B | `legacy_seeds`, from the WEX1 form of the same checkpoint (`repack_v4_wex.py`, format 1) | 3 WNR2 with a WNM2 model trained on the experts (weight and scale chunks 2048/512, 512/256, 16384/16384), 1 alias |

`legacy_seeds` is a program that `run.sh` builds from `legacy_seeds.c` before the seeds are made, with the compiler of the mode (gcc or `CC` with `WEX_CFLAGS` for `--replay`, clang or `CC` for a fuzzing run). The tools of this repository that write WNR or WNR2 records need a GPU (`c/tools/wex_neural_rans.py` loads a CUDA encoder, `archive/nr2/` a CUDA library), so `legacy_seeds` encodes on the CPU:

- WNR: `make_seeds.py` runs `repack_v4_wex.py` unchanged and replaces only its encoder class, as `c/tests/test_repack_v4_wex.py` does. The writer frames the container as it always does: header flags tiles, dedup and WNR, one model for every record, the raw expert, the alias. `legacy_seeds model` trains that model (4 classes over the scale values 114 to 127 of the experts, 17 CDFs per class from the counts of all experts; the scale-only model has one CDF per class, repeated in its 17 rows). `legacy_seeds record` encodes each record with `fuzz_wnr1_encode` of `legacy_mutator.h` and decodes it back with the decoder of `c/wex_neural_rans.h` before the writer gets it. `make_seeds.py` then checks the container with the writer's `validate_container` and decodes every WNR record once more with the Python decoder of `c/tools/wex_neural_rans.py`, which shares no code with that encoder.
- WNR2: no tool of this repository writes a WNR2 container on the CPU, so `legacy_seeds wnr2` writes the whole file, with the reference encoder `wex_nr2_encode` of `c/wex_neural_rans.h`. Before it writes the file it checks the header, the table, the model descriptor, the model and its id as the store does when it opens a file, and decodes every record with the model read back from the new file.

Every record must decode to the bytes of its expert. The random build id that `repack_v4_wex.py` writes at bytes 40 to 55 is set to zero, so the four files are the same bytes on every run: two runs of `make_seeds.py` on Windows wrote the same four SHA-256 names, and the seven CI jobs that ran `--replay` before the ARM64 and macOS sanitizer jobs were merged (Linux x86-64 and ARM64, macOS, Windows, three sanitizer builds; 2026-11-15) printed the same counts for them. Without its second argument `make_seeds.py` writes only the palette container. Everything is written under `wex4/fuzz/out/`, which is git-ignored: `corpus/<run>/` holds the inputs libFuzzer kept and is reused by the next run, until the folder is deleted.

## When a harness stops

`run.sh` prints the end of the run's log and exits 1. The input is in `wex4/fuzz/out/crashes/`, named `<run>-crash-<sha1>` (or `-oom-`, `-timeout-`; the run is the harness's name, or `fuzz_store_wex-legacy`, whose harness is `fuzz_store_wex`), and the log names what happened: a sanitizer report with a stack, or a line `ORACLE FAILED: ...` for one of the properties of the table. To see it again:

```sh
wex4/fuzz/out/fuzz_wex4_file wex4/fuzz/out/crashes/fuzz_wex4_file-crash-<sha1>
```

A crash file is a hostile input by construction. One found on your own machine is reported as [SECURITY.md](../../SECURITY.md) says, not in a public issue, unless it is only a failed oracle with no memory error. One found by the CI run is public already: the job prints the end of the log and keeps the reproducer as an artifact of a public run: `fuzz-crashes` (x86-64 Linux), `fuzz-crashes-arm` (ARM64 Linux) or `fuzz-crashes-macos`. A file that the readers must refuse and that no vector covers is a candidate for [`../vectors/`](../vectors/README.md).

## Limits

- `fuzz_wex4_file.c` does not decode a file whose header claims more than 64 MiB for one record (`FUZZ_MAX_DECODED`). The format allows 2^30 bytes; the harness would spend its time filling memory. Such a file is still validated up to that point.
- `fuzz_store_wex.c` does not open a container that the validators accept and whose slabs would take more than 64 MiB (`FUZZ_MAX_SLABS`: the store allocates 24 slabs of `aligned_expert_bytes` per layer when it opens, also for a layer without records, so a table of many layers reaches that with small records). Since 2026-11-15 `wex_validate_table` refuses a WEX1 or WEX2 header whose `aligned_expert_bytes` is more than twice the largest 4096-aligned decoded record of its table (before, the header could state anything up to 4 GiB whatever its records were, and the harness skipped every input whose header asked for more than 64 MiB, valid or not); an input with such a header now goes to the store, which must refuse it. The counts of the table above were measured before this change. `fuzz_q38_wex.c` does not attach a grid of more than 4096 experts or a record of more than 16 MiB. It looks up or loads at most 64 experts of a container.
- The mirrors, the read splits, the striped read, `WEX_READ_RETRY` and `DSV4_CUDA_MOE_MASKED` are fuzzed through the second passes; reads that fail (the second read of `WEX_READ_RETRY=1` that succeeds among them) and the root pin of `COLI_WEX_ROOT` through the third. The 16 ms pause of `c/expert_store_wex.c` before the second read of `WEX_READ_RETRY=1` (`wex_retry_pause`) does not wait in `fuzz_store_wex`: `read_faults.h` replaces its `Sleep` and `nanosleep` with a counter, and the third pass checks that a lookup whose read failed pauses exactly once with `WEX_READ_RETRY=1` and never without it. Up to commit `1d1874e` the harness took these pauses: in the 60 s run of the Fuzz workflow on commit `1d1874e` (run [43769004343](https://github.com/KairaCode/Wex-WRN2/actions/runs/43769004343), once, shared runner) its counters show at least 1318 loads read again after a pause (572 + 536 lookups of the third pass, 210 of the second; prefetches are not counted), so at least 21 s of the 60 s asleep (worked out from the counts, not timed). The next run, on commit `2e597c3` with the pauses skipped (run [43797767857](https://github.com/KairaCode/Wex-WRN2/actions/runs/43797767857), once), skipped 1325 pauses, but does not show a gain: `fuzz_store_wex` executed 17,041 inputs against 17,636, while between the same two runs `fuzz_wex4_verify`, which never pauses and did not change, fell from 87,621 to 48,216 and `fuzz_q38_wex`, which does not pause either, from 28,684 to 11,988: the shared runners vary more than the pauses cost, and one run of each does not measure it. A failed read there is an I/O error before any byte is read: a read that comes up short or returns other bytes than the file holds is not made, and a mirror whose own read fails at the attach of `c/qwen38_wex.h` (it is then ignored) is not tried. The CUDA helper's paths in `c/wex_decode.c` (its loader, the decode into host memory, the model registration) and the load wave of `c/qwen38_wex.h` are reached only on Windows, where `c/wex_decode.c` loads a helper, and only with the stand-in helper, which decodes on the CPU: they are replayed by `--replay`, never fuzzed (libFuzzer runs on Linux only). Not reached in the engine files: the helper's entry points that only the DeepSeek engine calls (decode into device memory, its batch form, host registration); the GPU code itself; the attach of `c/qwen38_wex.h` stopped by a failed read or a pinned root (the functions that refuse are called by the harness instead, see above); the Quark shards of `Q38_MXFP4_DIR`; unbuffered reads on Linux (`O_DIRECT` is not requested; Windows reads unbuffered but is only replayed; on macOS the file is opened through the stand-in `compat_open_direct` of `engine/q38_engine.h`, `open` and then `F_NOCACHE`, a guess at the engine's function); and the store opened through an engine (`coli_v4_expert_store_open_planned`).
- `fuzz_q38_wex` gives `COLI_WEX_WEIGHTS` no weight of `inf` and no weights whose sum is beyond the range of a double. With them `c/qwen38_wex.h` turns a NaN into an `int` when it computes the cuts, which C leaves undefined (on 2026-11-15 a build with gcc's `-fsanitize=float-cast-overflow` stopped there with `inf,1` and with `1e308,1e308`, and not with `1,1`). The engine code is unchanged; the fix is left to the maintainer.
- The older codecs in `fuzz_store_wex`: the WNR records of the seeds and of the mutator come from an encoder written in the harness from the decoder, not from the repository's WNR encoder (which needs CUDA), so a record that only that encoder would write is reached by mutation alone; the repository's writer frames the WNR containers around them. Every WNR record of the seeds has 4 classes and the model of its container, and the structured mutation keeps the count of classes (libFuzzer's own mutations can change it). The WNR2 records come from the reference encoder of `c/wex_neural_rans.h`, with a model trained on four small experts, not from the CUDA encoder of `archive/nr2/`. Each seed holds one coded codec, though a WEX3 header allows palette, WNR and WNR2 records side by side. The counts of the section above come from 60 s runs only.
- The mutators replace a record inside a container only when the new one takes the same number of pages, and they do not change the header, the table or the WNM2 model of a container (libFuzzer's own mutations do).
- The harnesses run on one thread and are built without `-fopenmp` (`fuzz_wnr3_cuda` adds one host thread per CUDA thread of a block that has a barrier, see above): the parallel paths of `wex4_verify.c` and of the fast decoder are not fuzzed. They are run once on the seeds, not fuzzed, under ThreadSanitizer with `-fopenmp` and under MemorySanitizer by [`../../scripts/sanitize_c.sh`](../../scripts/README.md), which calls `run.sh --replay` with `CC=clang` and its flags in `WEX_CFLAGS`.
- The GPU decoder (`c/wex_cuda.cuh`) is fuzzed as host C++ through the emulation of `cuda_host.h`, and its kernels are replayed with the mutator on an NVIDIA GPU by hand (`--gpu`, from the PTX of clang, not of nvcc), never under coverage guidance on a GPU; and only its WNR3 path: the WNR2 path of the same kernels, and the WNR1 and palette kernels, are compiled and not run (no seed holds such a record). The emulation runs an operation whole, so a kernel that reads bytes while a copy on another stream writes them is not seen: kernel A reads the word that holds the last byte of the last scale stream, and up to 3 bytes of that word belong to the weight payload, which may still be in flight (a stream that decodes right never uses them). The GPU run has that overlap; that its bytes were right says the race changed no result there, not that it cannot. `cuda_negative.py` shows that the harness notices 23 kinds of broken decoder, not that it notices every kind.
- CI (`.github/workflows/fuzz.yml`) runs each of the seven runs for 60 seconds (the store harness twice): enough to notice a harness that no longer builds or a shallow bug, not a substitute for a long run (for `fuzz_wnr3_cuda`, 421 and 256 inputs in the two x86-64 runs of 2026-11-15, [43717913457](https://github.com/KairaCode/Wex-WRN2/actions/runs/43717913457) and [43769081058](https://github.com/KairaCode/Wex-WRN2/actions/runs/43769081058), before it ran on ARM64 and macOS). It builds with clang on x86-64 Linux and on 64-bit ARM Linux (the distribution's clang) and on macOS (Apple silicon, the clang of the highest `llvm@N` of Homebrew on the runner image, `llvm@18` on 2026-11-15), one job each; on Windows the harnesses only run `--replay`, which has no coverage guidance. No Intel Mac.
