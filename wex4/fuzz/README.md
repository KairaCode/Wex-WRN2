# wex4/fuzz/

**Current.** Coverage-guided fuzzing harnesses for the C readers and decoders, for [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (and AFL++ through its libFuzzer driver). They complement the in-process mutation fuzzer of [`../wex4_tools.c`](../wex4_tools.c) (`wex4_fuzz_run`, run by [`../build_and_test.sh`](../build_and_test.sh)): that one applies a fixed number of random edits to three files on every run of the tests; these keep the inputs that reach new code and can run for hours.

| Harness | Input | Code under test | What must hold, besides the sanitizers |
|---|---|---|---|
| `fuzz_wex4_file.c` | a whole WEX4 file | `c/wex4.h`: header page, index, RAW / WBP1 / WNR3 record decoding, through `check_impl` of `wex4_tools.c` | each input is checked as it is (every hash verified) and again with the header and index hashes recomputed and the records decoded without their hash, so that a mutation reaches the validators and the decoders. A file accepted with its hashes decodes to the same content digest without them; decoding twice gives the same digest; a file whose records decode has a header page and an index that validate |
| `fuzz_wnr3_record.c` | the stored bytes of one WNR3 record | `wex_nrx_parse` and `wex_nr2_decode` (`c/wex_neural_rans.h`), `wex_fast_decode` (`../research/fast-cpu-decode/wex_fast_decode.h`) | the reference and the fast decoder give the same verdict, and on success the same bytes. The model and the layout come from the first WNR3 record of a real container (`WEX_FUZZ_BASE`, default `wex4/vectors/valid/tiny2-cz-upgraded.wex4`); the input is zero-padded to a multiple of 4096 bytes, up to that record's decoded size rounded up to 4096 |
| `fuzz_wex4_verify.c` | a whole WEX4 file | `c/tools/wex4_verify.c` (through a temporary file: the checker takes a path) | it answers "does not open as WEX4" exactly when `wex4_parse_header` or `wex4_open` refuses the same bytes, and the root of a file it passes is the SHA-256 of bytes [0, 4064) |
| `fuzz_store_wex.c` | a whole legacy container (WEX1, WEX2, WEX3) | `c/expert_store_wex.c` opened without an engine, with `c/wex_decode.c` and `c/wex_format.h` (through a temporary file named by `COLI_WEX_PATH`): open, lookup, release, prefetch, statistics, close; in a second pass (`store_paths.h`) the mirror of `COLI_MODEL_MIRROR`, the read split of `COLI_DISK_WEIGHTS`, `WEX_READ_RETRY` and `DSV4_CUDA_MOE_MASKED`; in a third pass the same with reads that fail (`read_faults.h`) | the store opens the file exactly when `wex_validate_header`, `wex_validate_table` and the model checks accept the same bytes in memory; a lookup succeeds exactly when the record's bytes pass the owner check and decode with `wex_decode_record` or `wex_decode_nr2_record`, and the three matrices it hands out are those decoded bytes; an expert that loaded loads again, and a cache hit reads no byte; the request, hit and miss counters add up. In the second pass: the store opens exactly when a mirror copy it takes has the input's size, header page and table (and refuses a canonical-zero container under `DSV4_CUDA_MOE_MASKED=1`), and every expert is read from the file the split names. In the third pass: an open with one of its reads failed fails; a prefetch whose read failed publishes nothing; a lookup whose read failed returns no record unless `WEX_READ_RETRY=1` read it again without a failure, and then it gives the record's verdict; the lookup after a failed one gives the record's verdict and bytes |
| `fuzz_q38_wex.c` | a whole container (WEX1, legacy WNR3, WEX4) | the container reader of the Qwen3.8 engine, `c/qwen38_wex.h`: `q38_wex_manifest`, `q38_wex4_manifest`, `q38_wex_entry_ok`, the model registration, `q38_expert_mx4_attach`, `q38_mx4_load` (a WEX4 file twice, without and with `COLI_WEX_VERIFY=1`); in a second pass (`q38_paths.h`) the mirrors of `COLI_WEX_EXTRA_MIRRORS`, the read split of `COLI_WEX_WEIGHTS`, the striped read of `COLI_WEX_STRIPE` and, with a CUDA helper, the load wave (`q38_mx4_decode_wave`); in a third pass reads that fail (`read_faults.h`) and the root pin of `COLI_WEX_ROOT` | the attach does not stop on a container whose manifest, entries and model the same functions accepted; every record of an attached container lies inside the file and its read fits its slab; a load stops the engine exactly when the record fails the first-read hash (when it is on), the owner check or `wex_decode_nr2_record`, and otherwise the slot holds exactly the decoded bytes. In the second pass: the attach takes, in order and at most three, exactly the mirror copies that differ from the input in record bytes only; the split's cuts are the weights' shares of 256; every load reads the drives the split names (a striped read cut on a page by the two drives' shares) and stops exactly when the bytes so read fail the same checks; a load wave stops exactly when one of its records does not decode. In the third pass: the manifest refuses a container when one of its reads fails, and a failed read of the model stops the engine; the manifest takes a WEX4 file under its own root (in any case) and refuses it under another, and refuses a legacy file under any root; a load whose read failed (either half of a striped read) stops the engine, and the load after it gives the record's verdict and bytes |

## The two engine harnesses

`c/expert_store_wex.c` and `c/qwen38_wex.h` are engine files: they include headers that are not in this repository, and their own tests (`c/tests/test_expert_store_wex.c`, `c/tests/test_qwen38_mxfp4.c`) build only inside an engine tree. The harnesses build them here against the stand-ins of [`engine/`](engine/):

The stand-ins were compared on 2026-11-15 with [colibri](https://github.com/JustVugg/colibri) `dev` at commit `98327913f980514970173b6df7bf67210ad0dc16` (2026-11-15), and, for the Qwen3.8 types, with the open colibri pull request #2825 (commit `5e0a0b5`, MXFP4 experts read from a sidecar). Each declaration cites the colibri file and line it follows.

- `engine/expert_store.h`, `engine/deepseek_v4_internal.h` and `engine/compat.h` stand for the engine headers of those names and for the `tensor.h`, `deepseek_v4.h` and `expert_store_registry.h` they include. Every type, member and enumerator the store uses has colibri's name, type and order. `engine/compat.h` declares nothing: the store uses nothing of colibri's `compat.h`. The harness defines the two engine functions the store calls: `coli_v4_expert_store_open_planned` (it opens nothing; colibri's opens the RAM-tiered store of an engine) and `coli_expert_store_backend_register` (it records nothing).
- `engine/q38_engine.h` declares the engine types `c/qwen38_wex.h` names. What `c/qwen38_wex.h` takes from colibri's `compat.h` and `st.h` is copied, with its line. That includes `compat_open_direct`, which `c/qwen38_wex.h` calls on macOS, where there is no `O_DIRECT`: it opens the file read-only and sets `F_NOCACHE` (colibri `c/compat.h:59-63`; issue #22). The configuration, the weight, the slot, the model and the expert index have colibri's types and order for every member colibri has. Inferred, because no public tree has them: the members `c/qwen38_wex.h` adds to the expert index (`mx`, `mx_*`, `wex_*`), the weight's `e8` (pull request #2825 holds the same bytes in a member named `x2q`), the value of `Q38_WEIGHT_MXFP4` (10, as in #2825) and `q38_slab_unpin`. A difference between these and the engine's types is one this harness cannot see. No public colibri tree includes `c/qwen38_wex.h`, so it cannot be built inside colibri itself.
- What the comparison found in the stand-ins of 2026-11-14: `ColiTensorFormat` lacked its last three formats (`INT8_BLOCK`, `INT4_BLOCK`, `GGML`; the value of the one the store uses, `COLI_TENSOR_FP4_NATIVE_BLOCK`, was right); `ColiDeepSeekV4Config` was an incomplete struct where colibri has a complete typedef; `engine/compat.h` defined `Sleep` outside Windows, which colibri's `compat.h` does not, so the store did not build against colibri on Linux or macOS (it now has its own pause for `WEX_READ_RETRY`, `wex_retry_pause` in `c/expert_store_wex.c`); `st_tensor` had another member order, 4 dimensions where colibri has 8 and no `name` or `numel`; `Q38WeightKind` was `{F32 = 0, MXFP4}` where colibri starts with `NONE = 0` and has 10 kinds before MXFP4; `Q38Weight`, `Slot` and `Model` had their members in another order or lacked some; `q38_weight_free` and `q38_name` did nothing like colibri's; the Windows read of the stand-in had no event in its `OVERLAPPED` and made one read where colibri's loops over pieces below 2 GiB, and its last-error variable was not per thread. The stand-in `compat_open_direct` did what colibri's does. The replay passes with the stand-ins of both dates.
- `WEX_FUZZ_COLIBRI=fetch bash wex4/fuzz/run.sh --replay` (or `WEX_FUZZ_COLIBRI=<a colibri checkout>`) builds the two harnesses a second time against colibri's own headers in place of the stand-ins and replays their seeds (for `fuzz_q38_wex`: colibri's `compat.h` and `st.h`; its model types stay those of `engine/q38_engine.h`, checked against `qwen38_core.h` by reading, not by `engine_layout.c`). It also builds `engine_layout.c` against both: the program prints the offset, size and signedness of every member and the value of every enumerator of the declarations above, and the replay fails unless the two listings are equal. `fetch` takes the `c/*.h` of the pinned commit (`COLIBRI_COMMIT` in `run.sh`) with git into `out/colibri`; nothing of colibri is copied into this repository (colibri is under the Apache License 2.0, like this one). The listing does not cover the model types of `engine/q38_engine.h`, which no public colibri header declares in the form `c/qwen38_wex.h` needs, nor what a function does. The folder that `fetch` leaves, `out/colibri/c`, also holds colibri's `expert_store_registry.c`, so `bash scripts/build_cpu_check.sh wex4/fuzz/out/colibri/c` builds and runs the store's own test, `c/tests/test_expert_store_wex.c`, against colibri's files. Run on 2026-11-15, once each: on Windows 10 (MSYS2 UCRT64 gcc 16.2, against the same commit from a local clone: the replay and the store's test), and in the opt-in `colibri-headers` job of CI on Linux (ubuntu-24.04, gcc 13.3) and macOS (macos-15, Homebrew gcc 15.3), run [43768999583](https://github.com/KairaCode/Wex-WRN2/actions/runs/43768999583) of commit `1d1874e`: the 81 lines of `engine_layout.c` agreed, both harnesses replayed their seeds against colibri's headers, and the store's test passed. On macOS the Qwen3.8 harness built this way opens its files with colibri's own `compat_open_direct`. gcc 15.3 on macOS printed one `-Wformat-truncation` warning in colibri's `st.h` (line 713), none in this repository's files. Later on 2026-11-15 colibri `dev` was at `1a06018699d5ca18040797e31ad4b7baf12260a2`, 33 commits on, with none of the nine files the stand-ins cite changed (`tensor.h`, `expert_store.h`, `deepseek_v4.h`, `deepseek_v4_internal.h`, `expert_store_registry.h`, `expert_store_registry.c`, `compat.h`, `st.h`, `qwen38_core.h`; `git diff` between the two commits), and pull request #2825 was still open at `5e0a0b5`. The replay against that commit's headers and the store's test against its files passed too (Windows 10, MSYS2 UCRT64 gcc 16.2, once, `WEX_FUZZ_COLIBRI` naming a sparse checkout of it); the pin in `run.sh` stays at `98327913`.
- The engine stops with `exit(1)` on a container it refuses. In `fuzz_q38_wex.c` an `exit` inside `c/qwen38_wex.h` returns to the harness (`longjmp`), which first runs the same checks without the exit and calls the real attach only on a container that passed them. The geometry (layers, experts, hidden and intermediate size) is taken from the input, where the engine takes it from the model's configuration.
- Both harnesses empty the model registry of `c/wex_decode.c` (16 models for the life of the process) before every input, and send the log lines of the code under test nowhere.
- Both make a second pass over every container that opened, through the read paths the first pass leaves alone (`store_paths.h`, `q38_paths.h`, with what they share in `engine_paths.h`). A mirror is a copy of the input in a directory of its own, in one of six forms: the same bytes, one byte changed in every page of every record, one byte changed in the header page or in the table (or the WEX4 index), a page appended, no file; or the input's own directory. The form says whether the code under test must take the copy, and a copy whose records differ shows a read from the wrong drive, or a striped read cut at the wrong page. Which form, weights and switches an input gets depends on its bytes only, so a crash file replays the same way. Each new check was broken once on purpose, in a copy of the harness (ten edits of what the harness expects. Qwen3.8: the drive, the stripe off, the stripe cut at the middle page, the weights, the copies taken, the first-read hash, the decode of a wave, with the stand-in helper. Store: the drive, the cut, the bytes compared); each edit made the replay of the seeds fail (2026-11-15, Windows, gcc 16.2, once each; the scripts of that check are not in the repository).
- Both then make a third pass, with reads that fail. `read_faults.h`, included right before the engine file, sends that file's reads through two wrappers (`pread`; on Windows `ReadFile`, and `pread` where the engine's `compat.h` defines it as `compat_pread`) that let a given number of reads through and fail the next one or two, as an I/O error. A pass first counts the reads of a clean call, then fails one of them. The store is opened with one of its reads failed (header page, table, model, the mirror's header page and table), an expert is prefetched with its read failed, then looked up with its read failed, with `WEX_READ_RETRY` off, or on with one read failed (so the second read succeeds) or two. For `c/qwen38_wex.h` the harness calls `q38_wex_manifest` and `q38_wex_model` itself with one read failed, and `q38_wex_manifest` under `COLI_WEX_ROOT` set to the WEX4 file's own root (in capitals for one input in 2), to that root with one digit changed, and, for a legacy file, to a root of zeros; then it loads one expert alone with one of its reads failed (either half of a striped read). A refused manifest is checked by calling it, not the attach: there the engine exits, holding a page, a table and a descriptor that the harness, which goes on, would leak. The checks were broken on purpose in copies of the engine files, nine edits of the code under test, each in its own copy (store: a failed read not seen; no second read under `WEX_READ_RETRY`; the second read not checked; a prefetch that publishes a failed load. Qwen3.8: a failed read not seen by `q38_wex_read`; a load that ignores a failed read; a striped read that ignores its second half, Windows code; the root pin ignored on WEX4; on a legacy file). Each made the replay of the seeds stop with a failed oracle, the prefetch one with an oracle of the second pass, which runs first (2026-11-15, Windows 10, MSYS2 UCRT64 gcc 16.2, once each; the script of that check is not in the repository). In one `--replay` (the seeds and the mutator's inputs made from them; Windows 10, gcc 16.2, 2026-11-15) the pass of the store refused 262 opens with a failed read and made 262 lookups with a failed read, 28 of them read again and served; that of Qwen3.8 refused 106 manifests, stopped 22 model reads and 106 loads (41 of them striped), and took 33 root pins and refused 106.

Every line of `c/expert_store_wex.c`, `c/qwen38_wex.h`, `c/wex_decode.c`, `c/wex_format.h` and `c/wex4.h` that the harnesses run is the real one.

## The WNR3-aware mutator and the dictionary

A WNR3 stream starts at a state that holds a 23-bit hash of the bytes it decodes to, and the decoder requires that state at its end. A byte changed in a stored record fails the first stream it touches, so with libFuzzer's own mutations the fuzzer reaches the decode loops and nothing behind an accepted stream. `wnr3_mutator.h` mutates on the other side of the codec: it decodes the record, edits the decoded scales and weights and the record's parameters (chunk sizes, owner, anchors, flags), and encodes the result with the reference encoder, which writes the right hash into every stream. Two calls in three it encodes the canonical way (canonical zero, ceil form); one in three it draws the flag bits at random, so that a record with right hashes is still refused later (a -0 under the canonical-zero flag, a scale of 0 in a block the ceil inverse has to undo).

Four harnesses define `LLVMFuzzerCustomMutator` with it; every other call is libFuzzer's own mutation (`LLVMFuzzerMutate`):

| Harness | Structured calls | What they change |
|---|---|---|
| `fuzz_wnr3_record` | 2 in 3 | the input record, or the base record when the input does not decode |
| `fuzz_store_wex` | 1 in 4 | one WNR3 record of a legacy container that opens, in place, when the new record takes the same pages |
| `fuzz_q38_wex` | 1 in 4 | the same, and one WNR3 record of a WEX4 file that opens; its SHA-256 in the index is left alone, so the record loads without `COLI_WEX_VERIFY` and stops the engine with it |
| `fuzz_wex4_file` | 1 in 4 | one WNR3 record of the input as the second check sees it (header and index hashes recomputed) |

`fuzz_wex4_verify` has none: the checker verifies the SHA-256 of every record, which a mutator cannot keep right without rewriting the index. `WEX_FUZZ_MUTATOR=0` in the environment turns the structured calls off.

`wex.dict` is a libFuzzer dictionary with the magic numbers of the containers, records and blobs and a few field values; `run.sh` passes it to the four harnesses whose input is a whole file.

Each harness with a mutator prints one line at exit with what the run reached. ## Running them

```sh
bash wex4/fuzz/run.sh            # 60 s per harness
bash wex4/fuzz/run.sh 14400      # 4 hours per harness
bash wex4/fuzz/run.sh --replay   # no fuzzing: gcc, every seed once through every harness
```

The first two need `clang` with libFuzzer, AddressSanitizer and UndefinedBehaviorSanitizer (`-fsanitize=fuzzer,address,undefined`): on Linux they are the compiler-rt runtimes (Debian and Ubuntu: `libclang-rt-N-dev`, which `clang` installs unless recommended packages are turned off; Fedora: `compiler-rt`); the MSYS2 UCRT64 clang does not accept `-fsanitize=fuzzer`, so on Windows use WSL or only `--replay`. `CC` names the compiler (`CC=clang-18`), `PYTHON` the interpreter (`PYTHON=python3` on Linux), as in the other scripts. `--replay` needs only `gcc` (or the compiler named in `CC`, for example a Homebrew `gcc-15` on macOS): it builds each harness with `-DWEX_FUZZ_STANDALONE`, which adds a `main` that runs the files named on its command line, and runs the seeds through it. A harness with a custom mutator also runs that mutator on every seed in `--replay` (200 inputs from each seed of `fuzz_wnr3_record`, 100 for `fuzz_store_wex`, 40 for `fuzz_wex4_file` and `fuzz_q38_wex`), with a small deterministic stand-in for `LLVMFuzzerMutate`: the mutator and the oracles behind it are tested without clang. On Windows `--replay` then runs `fuzz_store_wex` and `fuzz_q38_wex` a second time with a CUDA helper: the CPU stand-in `c/tests/fake_wex_cuda.c`, built as a DLL and named by `WEX_FUZZ_CUDA_LIB` (`c/wex_decode.c` loads a helper on Windows only). That run fails unless records were decoded through the helper. `WEX_FUZZ_COLIBRI` (above) adds the build against colibri's headers. Five jobs of `.github/workflows/ci.yml` run `--replay` after the CPU checks: gcc on x86-64 Linux, on 64-bit ARM Linux and on macOS (Apple silicon, a Homebrew GNU gcc; `--replay` prints the kernel of the fast decoder it built, and both ARM jobs fail unless it is NEON), on Windows, and on x86-64 Linux under AddressSanitizer and UndefinedBehaviorSanitizer. One `--replay` took 28 s on 2026-11-14 (Windows 10 desktop, MSYS2 UCRT64 gcc 16.2, one run). With the second and third passes and the runs with the helper of 2026-11-15 the replay step of the `windows` CI job took 21 s (windows-2022 runner, run 43768999583 of commit `1d1874e`, once, with the pauses of `WEX_READ_RETRY` still taken); it was not timed again on the desktop, which other builds shared that day.

The seeds are the conformance vectors ([`../vectors/`](../vectors/README.md)): every file of the manifest for the two WEX4 file harnesses, and the WNR3 records of the accepted ones for the record harness (`make_seeds.py`). The two engine harnesses get seven small expert containers that `make_seeds.py` writes: a WEX1 file and a WEX2 file made there, the legacy vector `tiny2-cz.wex3`, the same with its grid cut to its two experts, the WEX4 form of two of them, and a WEX1 file of 1 x 4 experts whose records are four pages long (so that a striped read is cut by its drives' shares, not only at its one-page minimum); `fuzz_q38_wex` also gets every file of the manifest. No seed holds palette (codec 2), WNR (codec 3) or WNR2 (codec 4) records. Everything is written under `wex4/fuzz/out/`, which is git-ignored: `corpus/<harness>/` holds the inputs libFuzzer kept and is reused by the next run, until the folder is deleted.

## When a harness stops

`run.sh` prints the end of the harness's log and exits 1. The input is in `wex4/fuzz/out/crashes/`, named `<harness>-crash-<sha1>` (or `-oom-`, `-timeout-`), and the log names what happened: a sanitizer report with a stack, or a line `ORACLE FAILED: ...` for one of the properties of the table. To see it again:

```sh
wex4/fuzz/out/fuzz_wex4_file wex4/fuzz/out/crashes/fuzz_wex4_file-crash-<sha1>
```

A crash file is a hostile input by construction. One found on your own machine is reported as [SECURITY.md](../../SECURITY.md) says, not in a public issue, unless it is only a failed oracle with no memory error. One found by the CI run is public already: the job prints the end of the log and keeps the reproducer as the artifact `fuzz-crashes` of a public run. A file that the readers must refuse and that no vector covers is a candidate for [`../vectors/`](../vectors/README.md).

## Limits

- `fuzz_wex4_file.c` does not decode a file whose header claims more than 64 MiB for one record (`FUZZ_MAX_DECODED`). The format allows 2^30 bytes; the harness would spend its time filling memory. Such a file is still validated up to that point.
- `fuzz_store_wex.c` does not open a container whose header would make the store allocate more than 64 MiB of slabs (`FUZZ_MAX_SLABS`: 24 slabs per layer of `aligned_expert_bytes` each, which a WEX1 or WEX2 header may set to anything up to 4 GiB whatever its records are). `fuzz_q38_wex.c` does not attach a grid of more than 4096 experts or a record of more than 16 MiB. It looks up or loads at most 64 experts of a container.
- The mirrors, the read splits, the striped read, `WEX_READ_RETRY` and `DSV4_CUDA_MOE_MASKED` are fuzzed through the second passes; reads that fail (the second read of `WEX_READ_RETRY=1` that succeeds among them) and the root pin of `COLI_WEX_ROOT` through the third. The 16 ms pause of `c/expert_store_wex.c` before the second read of `WEX_READ_RETRY=1` (`wex_retry_pause`) does not wait in `fuzz_store_wex`: `read_faults.h` replaces its `Sleep` and `nanosleep` with a counter, and the third pass checks that a lookup whose read failed pauses exactly once with `WEX_READ_RETRY=1` and never without it. Up to commit `1d1874e` the harness took these pauses: in the 60 s run of the Fuzz workflow on commit `1d1874e` (run [43769004343](https://github.com/KairaCode/Wex-WRN2/actions/runs/43769004343), once, shared runner) its counters show at least 1318 loads read again after a pause (572 + 536 lookups of the third pass, 210 of the second; prefetches are not counted), so at least 21 s of the 60 s asleep (worked out from the counts, not timed). A failed read there is an I/O error before any byte is read: a read that comes up short or returns other bytes than the file holds is not made, and a mirror whose own read fails at the attach of `c/qwen38_wex.h` (it is then ignored) is not tried. The CUDA helper's paths in `c/wex_decode.c` (its loader, the decode into host memory, the model registration) and the load wave of `c/qwen38_wex.h` are reached only on Windows, where `c/wex_decode.c` loads a helper, and only with the stand-in helper, which decodes on the CPU: they are replayed by `--replay`, never fuzzed (libFuzzer runs on Linux only). Not reached in the engine files: the helper's entry points that only the DeepSeek engine calls (decode into device memory, its batch form, host registration); the GPU code itself; the attach of `c/qwen38_wex.h` stopped by a failed read or a pinned root (the functions that refuse are called by the harness instead, see above); the Quark shards of `Q38_MXFP4_DIR`; unbuffered reads on Linux (`O_DIRECT` is not requested; Windows reads unbuffered but is only replayed); and the store opened through an engine (`coli_v4_expert_store_open_planned`).
- `fuzz_q38_wex` gives `COLI_WEX_WEIGHTS` no weight of `inf` and no weights whose sum is beyond the range of a double. With them `c/qwen38_wex.h` turns a NaN into an `int` when it computes the cuts, which C leaves undefined (on 2026-11-15 a build with gcc's `-fsanitize=float-cast-overflow` stopped there with `inf,1` and with `1e308,1e308`, and not with `1,1`). The engine code is unchanged; the fix is left to the maintainer. Palette, WNR and WNR2 records have decoders in `c/wex_format.h` that `fuzz_store_wex.c` can reach, but no seed and no mutator. `fuzz_store_wex` prints the records the store served by codec in its exit line: in the one 60 s run with the mutators made since it does ([43645082256](https://github.com/KairaCode/Wex-WRN2/actions/runs/43645082256), conditions as in the table above) they were 326 raw, 148 scale-tile, 2,218 WNR3 and no palette, WNR or WNR2 record. Not counted: the run without the mutators, and any longer run.
- The mutator does not write WNR2 records (the same streams without the hash), and it replaces a record inside a container only when the new one takes the same number of pages.
- The harnesses run on one thread and are built without `-fopenmp`: the parallel paths of `wex4_verify.c` and of the fast decoder are not fuzzed. They are run once on the seeds, not fuzzed, under ThreadSanitizer with `-fopenmp` and under MemorySanitizer by [`../../scripts/sanitize_c.sh`](../../scripts/README.md), which calls `run.sh --replay` with `CC=clang` and its flags in `WEX_CFLAGS`.
- The GPU decoder (`c/wex_cuda.cuh`) has no harness.
- CI (`.github/workflows/fuzz.yml`) runs each harness for 60 seconds: enough to notice a harness that no longer builds or a shallow bug, not a substitute for a long run. It builds with clang on x86-64 Linux only; on ARM, on macOS and on Windows the harnesses only run `--replay`, which has no coverage guidance.
