# wex4/fuzz/

**Current.** Coverage-guided fuzzing harnesses for the C readers and decoders, for [libFuzzer](https://llvm.org/docs/LibFuzzer.html) (and AFL++ through its libFuzzer driver). They complement the in-process mutation fuzzer of [`../wex4_tools.c`](../wex4_tools.c) (`wex4_fuzz_run`, run by [`../build_and_test.sh`](../build_and_test.sh)): that one applies a fixed number of random edits to three files on every run of the tests; these keep the inputs that reach new code and can run for hours.

| Harness | Input | Code under test | What must hold, besides the sanitizers |
|---|---|---|---|
| `fuzz_wex4_file.c` | a whole WEX4 file | `c/wex4.h`: header page, index, RAW / WBP1 / WNR3 record decoding, through `check_impl` of `wex4_tools.c` | each input is checked as it is (every hash verified) and again with the header and index hashes recomputed and the records decoded without their hash, so that a mutation reaches the validators and the decoders. A file accepted with its hashes decodes to the same content digest without them; decoding twice gives the same digest; a file whose records decode has a header page and an index that validate |
| `fuzz_wnr3_record.c` | the stored bytes of one WNR3 record | `wex_nrx_parse` and `wex_nr2_decode` (`c/wex_neural_rans.h`), `wex_fast_decode` (`../research/fast-cpu-decode/wex_fast_decode.h`) | the reference and the fast decoder give the same verdict, and on success the same bytes. The model and the layout come from the first WNR3 record of a real container (`WEX_FUZZ_BASE`, default `wex4/vectors/valid/tiny2-cz-upgraded.wex4`); the input is zero-padded to a multiple of 4096 bytes, up to that record's decoded size rounded up to 4096 |
| `fuzz_wex4_verify.c` | a whole WEX4 file | `c/tools/wex4_verify.c` (through a temporary file: the checker takes a path) | it answers "does not open as WEX4" exactly when `wex4_parse_header` or `wex4_open` refuses the same bytes, and the root of a file it passes is the SHA-256 of bytes [0, 4064) |
| `fuzz_store_wex.c` | a whole legacy container (WEX1, WEX2, WEX3) | `c/expert_store_wex.c` opened without an engine, with `c/wex_decode.c` and `c/wex_format.h` (through a temporary file named by `COLI_WEX_PATH`): open, lookup, release, prefetch, statistics, close | the store opens the file exactly when `wex_validate_header`, `wex_validate_table` and the model checks accept the same bytes in memory; a lookup succeeds exactly when the record's bytes pass the owner check and decode with `wex_decode_record` or `wex_decode_nr2_record`, and the three matrices it hands out are those decoded bytes; an expert that loaded loads again, and a cache hit reads no byte; the request, hit and miss counters add up |
| `fuzz_q38_wex.c` | a whole container (WEX1, legacy WNR3, WEX4) | the container reader of the Qwen3.8 engine, `c/qwen38_wex.h`: `q38_wex_manifest`, `q38_wex4_manifest`, `q38_wex_entry_ok`, the model registration, `q38_expert_mx4_attach`, `q38_mx4_load` (a WEX4 file twice, without and with `COLI_WEX_VERIFY=1`) | the attach does not stop on a container whose manifest, entries and model the same functions accepted; every record of an attached container lies inside the file and its read fits its slab; a load stops the engine exactly when the record fails the first-read hash (when it is on), the owner check or `wex_decode_nr2_record`, and otherwise the slot holds exactly the decoded bytes |

## The two engine harnesses

`c/expert_store_wex.c` and `c/qwen38_wex.h` are engine files: they include headers that are not in this repository, and their own tests (`c/tests/test_expert_store_wex.c`, `c/tests/test_qwen38_mxfp4.c`) build only inside an engine tree. The harnesses build them here against the stand-ins of [`engine/`](engine/):

- `engine/expert_store.h`, `engine/deepseek_v4_internal.h` and `engine/compat.h` declare what `c/expert_store_wex.c` uses of the engine headers of those names (the tensor and expert views, the store's function table, the open options, `Sleep`). The first two follow colibri's headers. The harness defines the two engine functions the store calls: `coli_v4_expert_store_open_planned` (never opens anything) and `coli_expert_store_backend_register` (records nothing). On 2026-11-14 the harness also built against the headers of a colibri checkout (commit `0a5504a`) in place of the stand-ins and replayed its seeds (Windows, MSYS2 UCRT64 gcc 16.2, `--replay` only; not run on Linux, where that tree's `compat.h` has no `Sleep`).
- `engine/q38_engine.h` declares the engine types `c/qwen38_wex.h` names: the configuration, the model, the expert slot, the weight, the expert index with its `wex_*` and `mx_*` members. Those members are in no public tree, so their types are inferred from how `c/qwen38_wex.h` uses them. A difference between a stand-in type and the engine's (a width, a signedness) is a difference this harness cannot see. `c/qwen38_wex.h` cannot be built against the real engine from this repository. On macOS, which has no `O_DIRECT`, `c/qwen38_wex.h` opens the file through the engine's `compat_open_direct`; the stand-in opens it and sets `F_NOCACHE`, which is a guess at what the engine's function does.
- The engine stops with `exit(1)` on a container it refuses. In `fuzz_q38_wex.c` an `exit` inside `c/qwen38_wex.h` returns to the harness (`longjmp`), which first runs the same checks without the exit and calls the real attach only on a container that passed them. The geometry (layers, experts, hidden and intermediate size) is taken from the input, where the engine takes it from the model's configuration.
- Both harnesses empty the model registry of `c/wex_decode.c` (16 models for the life of the process) before every input, and send the log lines of the code under test nowhere.

Every line of `c/expert_store_wex.c`, `c/qwen38_wex.h`, `c/wex_decode.c`, `c/wex_format.h` and `c/wex4.h` that the harnesses run is the real one.

## The custom mutators and the dictionary

A WNR3 stream starts at a state that holds a 23-bit hash of the bytes it decodes to, and the decoder requires that state at its end. A byte changed in a stored record fails the first stream it touches, so with libFuzzer's own mutations the fuzzer reaches the decode loops and nothing behind an accepted stream. `wnr3_mutator.h` mutates on the other side of the codec: it decodes the record, edits the decoded scales and weights and the record's parameters (chunk sizes, owner, anchors, flags), and encodes the result with the reference encoder, which writes the right hash into every stream. Two calls in three it encodes the canonical way (canonical zero, ceil form); one in three it draws the flag bits at random, so that a record with right hashes is still refused later (a -0 under the canonical-zero flag, a scale of 0 in a block the ceil inverse has to undo).

`legacy_mutator.h` does the same for the older record codecs, in `fuzz_store_wex`. What a changed byte does to each of them, and what the mutation does instead:

- Scale tiles (codec 1) and palette (codec 2): the scales are a tile stream (per 256 scales a base, a bit width and the packed differences) that must end exactly at its stored length, so a changed width usually refuses the record. The mutation unpacks the scales, edits a few and packs them again, one tile in four with a wider width and a lower base that decode to the same values. In a palette record it also changes a few bytes of the three tables and of the packed 3-bit weights, which have no check: every value decodes.
- WNR (codec 3): the record holds its own model (a class per scale value, 17 CDFs of 16 symbols per class) and one rANS stream per 256, 512 or 1024 weights, which must end at its length with the state back at 2^23, so a changed payload byte almost always refuses the record. The mutation decodes it, edits weights, scales, the class of a scale value (to another class, or one time in 8 to none), a CDF row, the chunk size and the scale-only flag, and encodes it again. A scale value that an edit brings in and that has no class gets one 7 times in 8. No tool of this repository encodes WNR records on the CPU (`c/tools/wex_neural_rans.py` calls a CUDA library), so the encoder, `fuzz_wnr1_encode`, is written in `legacy_mutator.h` from the decoder `wex_nr_decode_weights` of `c/wex_neural_rans.h`.
- WNR2 (codec 4): the streams of WNR3 without the hash, the flags and the owner, with the same end condition. `wnr3_mutator.h` edits it as it edits a WNR3 record and encodes it with the reference encoder; its three medians are recomputed, or one time in 8 drawn at random (any value decodes).

A record is replaced in place only when the new one takes the same pages and is not the same bytes; a record that two entries share (WEX3 deduplication) changes for both. A structured call decodes the record first, so a record that the decoder refuses is not mutated again by structured calls, only by libFuzzer's own mutations.

Some WNR edits make a record that the decoder refuses, on purpose: a scale value left without a class (the encoder codes it with class 0 and the decoder stops at it), or the scale-only flag set over CDF rows that differ (the parser refuses it). The exit line of `fuzz_store_wex` counts, by codec, the replaced records that the store's checks refuse. A test program that is not in the repository called `fuzz_legacy_mutate` 20,000 times for each seed of `seeds/legacy/` and `seeds/engine/`, each time on a fresh copy of the seed, and decoded each rewritten record (Windows 10, MSYS2 UCRT64 gcc 16.2, run once). Of the WNR records it rewrote, 9.8% were refused in the seed with a context model (1,812 of 18,402: 887 with the scale-only flag over rows that differ, 925 with a scale without a class) and 5.5% in the seed with a scale-only model (861 of 15,621: 5 and 856). No refused WNR record had another cause: none failed in a rANS stream. Every palette (19,998), WNR2 (18,560) and scale-tile (19,999) record it rewrote was accepted. WNR3 records, rewritten by `wnr3_mutator.h` with flag bits drawn at random one time in three, were refused 29.6% of the time (5,896 of 19,918).

Four harnesses define `LLVMFuzzerCustomMutator`; every other call is libFuzzer's own mutation (`LLVMFuzzerMutate`):

| Harness | Structured calls | What they change |
|---|---|---|
| `fuzz_wnr3_record` | 2 in 3 | the input record, or the base record when the input does not decode |
| `fuzz_store_wex` | 1 in 4 | one coded record of a legacy container that opens (scale tiles, palette, WNR, WNR2 or WNR3, each with the mutation of its codec), in place, when the new record takes the same pages |
| `fuzz_q38_wex` | 1 in 4 | one WNR3 record of a legacy container that opens, in place, when the new record takes the same pages, and one WNR3 record of a WEX4 file that opens; its SHA-256 in the index is left alone, so the record loads without `COLI_WEX_VERIFY` and stops the engine with it |
| `fuzz_wex4_file` | 1 in 4 | one WNR3 record of the input as the second check sees it (header and index hashes recomputed) |

`fuzz_wex4_verify` has none: the checker verifies the SHA-256 of every record, which a mutator cannot keep right without rewriting the index. `WEX_FUZZ_MUTATOR=0` in the environment turns the structured calls off.

`wex.dict` is a libFuzzer dictionary with the magic numbers of the containers, records and blobs, the legacy header flags as the writers combine them, the chunk sizes, the totals of the WNR and WNM2 CDFs and a few other field values; `run.sh` passes it to the four harnesses whose input is a whole file.

## Running them

```sh
bash wex4/fuzz/run.sh            # 60 s per run
bash wex4/fuzz/run.sh 14400      # 4 hours per run
bash wex4/fuzz/run.sh --replay   # no fuzzing: gcc, every seed once through every harness
```

There are six runs: one per harness, and a second run of `fuzz_store_wex`, named `fuzz_store_wex-legacy`, on the containers of the older codecs (`seeds/legacy/`) with a corpus of its own. The first run of `fuzz_store_wex` starts from the engine seeds alone, so the older codecs do not take the time of its WNR3 records (see the measurements above).

The first two need `clang` with libFuzzer, AddressSanitizer and UndefinedBehaviorSanitizer (`-fsanitize=fuzzer,address,undefined`): on Linux they are the compiler-rt runtimes (Debian and Ubuntu: `libclang-rt-N-dev`, which `clang` installs unless recommended packages are turned off; Fedora: `compiler-rt`); the MSYS2 UCRT64 clang does not accept `-fsanitize=fuzzer`, so on Windows use WSL or only `--replay`. Apple clang ships no libFuzzer runtime: on macOS name the clang of a Homebrew LLVM (`CC=$(brew --prefix llvm@18)/bin/clang`, which brings libFuzzer and both sanitizers; the Fuzz workflow takes the highest `llvm@N` of the runner image). That line was not run on a Mac of your own: CI used the `llvm@18` already on the runner image, and neither `brew install llvm@18` nor the step of the workflow that runs `brew install llvm` when the image has no `llvm@N` has run. `CC` names the compiler (`CC=clang-18`), `PYTHON` the interpreter (`PYTHON=python3` on Linux and macOS), as in the other scripts. `--replay` needs only `gcc` (or the compiler named in `CC`, for example a Homebrew `gcc-15` or Apple clang on macOS): it builds each harness with `-DWEX_FUZZ_STANDALONE`, which adds a `main` that runs the files named on its command line, and runs the seeds through it. A harness with a custom mutator also runs that mutator on every seed in `--replay` (200 inputs from each seed of `fuzz_wnr3_record`, 100 for `fuzz_store_wex`, 40 for `fuzz_wex4_file` and `fuzz_q38_wex`), with a small deterministic stand-in for `LLVMFuzzerMutate`: the mutator and the oracles behind it are tested without clang. Seven jobs of `.github/workflows/ci.yml` run `--replay` after the CPU checks: gcc on x86-64 Linux, on 64-bit ARM Linux and on macOS (Apple silicon, a Homebrew GNU gcc), on Windows, and under AddressSanitizer and UndefinedBehaviorSanitizer on x86-64 Linux and on 64-bit ARM Linux (`linux-sanitizers`, `linux-arm-sanitizers`); and Apple clang on macOS, once as it is and once under both sanitizers (`macos-clang`). `--replay` prints the compiler and the kernel of the fast decoder it built, and every ARM64 job fails unless it is NEON. One `--replay` took 28 s on 2026-11-14 (Windows 10 desktop, MSYS2 UCRT64 gcc 16.2, one run), 28 s again on 2026-11-15 with the seeds of the older codecs and the build of `legacy_seeds`, and 33 s with the WNR seeds written by `repack_v4_wex.py` and the second store run (same machine and compiler, one run each).

The seeds are the conformance vectors ([`../vectors/`](../vectors/README.md)): every file of the manifest for the two WEX4 file harnesses, and the WNR3 records of the accepted ones for the record harness (`make_seeds.py`). The two engine harnesses get eight small expert containers that `make_seeds.py` writes: a WEX1 file and a WEX2 file made there, the legacy vector `tiny2-cz.wex3`, the same with its grid cut to its two experts, the WEX4 form of two of them, and the WEX1 file twice more with the slab size of its header changed (twice its record, which is the most the validators accept, and 4 GiB - 4096, which they refuse); `fuzz_q38_wex` also gets every file of the manifest. The run `fuzz_store_wex-legacy` gets, in their place, four WEX3 containers of the older codecs (`seeds/legacy/`; the Qwen3.8 reader takes none of them). Each holds one layer of the same four MXFP4 experts, which `make_seeds.py` makes (hidden and intermediate size 128, a slab of 28,672 bytes; the fourth is a copy of the first, and the third has a scale of 255 in each of its three matrices):

| Container | Written by | Records |
|---|---|---|
| palette, 86,016 B | `c/tools/repack_v4_wex.py` (format 3, `palette3`, any error allowed), from a safetensors checkpoint of the four experts | 2 palette, 1 raw (the writer does not quantize an expert with a scale of 255), 1 alias |
| WNR with a context model, 86,016 B | `repack_v4_wex.py` (format 3, `neural-rans`, chunks of 512 symbols), from the same checkpoint, with `legacy_seeds` in place of its CUDA encoder | 2 WNR, 1 raw (the model has no class for 255, so the writer does not code that expert), 1 alias |
| WNR with a scale-only model, 86,016 B | the same, chunks of 1024 symbols | 2 WNR, scale-only, 1 raw, 1 alias |
| WNR2, 131,072 B | `legacy_seeds`, from the WEX1 form of the same checkpoint (`repack_v4_wex.py`, format 1) | 3 WNR2 with a WNM2 model trained on the experts (weight and scale chunks 2048/512, 512/256, 16384/16384), 1 alias |

`legacy_seeds` is a program that `run.sh` builds from `legacy_seeds.c` before the seeds are made, with the compiler of the mode (gcc or `CC` with `WEX_CFLAGS` for `--replay`, clang or `CC` for a fuzzing run). The tools of this repository that write WNR or WNR2 records need a GPU (`c/tools/wex_neural_rans.py` loads a CUDA encoder, `archive/nr2/` a CUDA library), so `legacy_seeds` encodes on the CPU:

- WNR: `make_seeds.py` runs `repack_v4_wex.py` unchanged and replaces only its encoder class, as `c/tests/test_repack_v4_wex.py` does. The writer frames the container as it always does: header flags tiles, dedup and WNR, one model for every record, the raw expert, the alias. `legacy_seeds model` trains that model (4 classes over the scale values 114 to 127 of the experts, 17 CDFs per class from the counts of all experts; the scale-only model has one CDF per class, repeated in its 17 rows). `legacy_seeds record` encodes each record with `fuzz_wnr1_encode` of `legacy_mutator.h` and decodes it back with the decoder of `c/wex_neural_rans.h` before the writer gets it. `make_seeds.py` then checks the container with the writer's `validate_container` and decodes every WNR record once more with the Python decoder of `c/tools/wex_neural_rans.py`, which shares no code with that encoder.
- WNR2: no tool of this repository writes a WNR2 container on the CPU, so `legacy_seeds wnr2` writes the whole file, with the reference encoder `wex_nr2_encode` of `c/wex_neural_rans.h`. Before it writes the file it checks the header, the table, the model descriptor, the model and its id as the store does when it opens a file, and decodes every record with the model read back from the new file.

Every record must decode to the bytes of its expert. The random build id that `repack_v4_wex.py` writes at bytes 40 to 55 is set to zero, so the four files are the same bytes on every run: two runs of `make_seeds.py` on Windows wrote the same four SHA-256 names, and the seven CI jobs that ran `--replay` before the ARM64 and macOS sanitizer jobs were merged (Linux x86-64 and ARM64, macOS, Windows, three sanitizer builds; 2026-11-15) printed the same counts for them. Without its second argument `make_seeds.py` writes only the palette container. Everything is written under `wex4/fuzz/out/`, which is git-ignored: `corpus/<run>/` holds the inputs libFuzzer kept and is reused by the next run, until the folder is deleted.

## When a harness stops

`run.sh` prints the end of the run's log and exits 1. The input is in `wex4/fuzz/out/crashes/`, named `<run>-crash-<sha1>` (or `-oom-`, `-timeout-`; the run is the harness's name, or `fuzz_store_wex-legacy`, whose harness is `fuzz_store_wex`), and the log names what happened: a sanitizer report with a stack, or a line `ORACLE FAILED: ...` for one of the properties of the table. To see it again:

```sh
wex4/fuzz/out/fuzz_wex4_file wex4/fuzz/out/crashes/fuzz_wex4_file-crash-<sha1>
```

A crash file is a hostile input by construction. One found on your own machine is reported as [SECURITY.md](../../SECURITY.md) says, not in a public issue, unless it is only a failed oracle with no memory error. One found by the CI run is public already: the job prints the end of the log and keeps the reproducer as an artifact of a public run: `fuzz-crashes` (x86-64 Linux), `fuzz-crashes-arm` (ARM64 Linux) or `fuzz-crashes-macos`. A file that the readers must refuse and that no vector covers is a candidate for [`../vectors/`](../vectors/README.md).

## Limits

- `fuzz_wex4_file.c` does not decode a file whose header claims more than 64 MiB for one record (`FUZZ_MAX_DECODED`). The format allows 2^30 bytes; the harness would spend its time filling memory. Such a file is still validated up to that point.
- `fuzz_store_wex.c` does not open a container that the validators accept and whose slabs would take more than 64 MiB (`FUZZ_MAX_SLABS`: the store allocates 24 slabs of `aligned_expert_bytes` per layer when it opens, also for a layer without records, so a table of many layers reaches that with small records). Since 2026-11-15 `wex_validate_table` refuses a WEX1 or WEX2 header whose `aligned_expert_bytes` is more than twice the largest 4096-aligned decoded record of its table (before, the header could state anything up to 4 GiB whatever its records were, and the harness skipped every input whose header asked for more than 64 MiB, valid or not); an input with such a header now goes to the store, which must refuse it. The counts of the table above were measured before this change. `fuzz_q38_wex.c` does not attach a grid of more than 4096 experts or a record of more than 16 MiB. It looks up or loads at most 64 experts of a container.
- Not fuzzed in the engine files: the mirror files and the striped read, `WEX_READ_RETRY`, the load wave and every path through the CUDA helper (`COLI_WEX_CUDA_LIB=0` is set), the Quark shards of `Q38_MXFP4_DIR`, unbuffered reads (`O_DIRECT` is not requested on Linux; Windows is only replayed; on macOS the file is opened through the stand-in `compat_open_direct` of `engine/q38_engine.h`, `open` and then `F_NOCACHE`, a guess at the engine's function), and the store opened through an engine (`coli_v4_expert_store_open_planned`).
- The older codecs in `fuzz_store_wex`: the WNR records of the seeds and of the mutator come from an encoder written in the harness from the decoder, not from the repository's WNR encoder (which needs CUDA), so a record that only that encoder would write is reached by mutation alone; the repository's writer frames the WNR containers around them. Every WNR record of the seeds has 4 classes and the model of its container, and the structured mutation keeps the count of classes (libFuzzer's own mutations can change it). The WNR2 records come from the reference encoder of `c/wex_neural_rans.h`, with a model trained on four small experts, not from the CUDA encoder of `archive/nr2/`. Each seed holds one coded codec, though a WEX3 header allows palette, WNR and WNR2 records side by side. The counts of the section above come from 60 s runs only.
- The mutators replace a record inside a container only when the new one takes the same number of pages, and they do not change the header, the table or the WNM2 model of a container (libFuzzer's own mutations do).
- The harnesses run on one thread and are built without `-fopenmp`: the parallel paths of `wex4_verify.c` and of the fast decoder are not fuzzed. They are run once on the seeds, not fuzzed, under ThreadSanitizer with `-fopenmp` and under MemorySanitizer by [`../../scripts/sanitize_c.sh`](../../scripts/README.md), which calls `run.sh --replay` with `CC=clang` and its flags in `WEX_CFLAGS`.
- The GPU decoder (`c/wex_cuda.cuh`) has no harness.
- CI (`.github/workflows/fuzz.yml`) runs each of the six runs for 60 seconds (the store harness twice): enough to notice a harness that no longer builds or a shallow bug, not a substitute for a long run. It builds with clang on x86-64 Linux and on 64-bit ARM Linux (the distribution's clang) and on macOS (Apple silicon, the clang of the highest `llvm@N` of Homebrew on the runner image, `llvm@18` on 2026-11-15), one job each; on Windows the harnesses only run `--replay`, which has no coverage guidance. No Intel Mac.
