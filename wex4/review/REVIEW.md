# Adversarial review of the WEX4 spec and prototype (2026-11-11)
Five reviewers, each with its own lens, then one verification pass per reviewer. Status says what was done about each confirmed finding in the commit that added this file; the scripts of the reviewers are in the subfolders.

## security-c

### S1 (major): Expert grid (num_layers x num_experts) is not tied to the expert records: a 12 KiB file makes the expert table 2^32 x 72 B = 288 GiB; the spec rule "0 when the file has no expert records" is enforced by no reader

- Where: c/wex4.h wex4_parse_header (only checks layers <= 65536, experts <= 65536, zero together) and wex4_open (only checks owner < grid); wex4/wex4_tools.c wex4_expert_table line `memset(out, 0, (size_t)v.h.layers * v.h.experts * sizeof(WexEntry))`; same gap in wex4/wex4.py Reader. Spec: docs/WEX4-SPEC.md section 4 (num_layers row), section 6 ("Nothing in the file can make it allocate more than that"), section 9 ("allocate without limit"), section 13.2 (engine fills a layers x experts WexEntry table).
- Verification: Reproduced. Both reviewer files (12,288 B, header layers=experts=65536, 1 record) return 0 from wex4_fuzz_check flags 3 in wex4/out/wex4_tools.dll and wex4_tools_ref.dll and are accepted by wex4.check with the same digest. My own files built with rvlib.build (one raw 16-byte tensor, no EXPERT record, grid 1x1, 65536x1, 65536x65536) are also accepted by all three. Code read: wex4.h line 161 only checks each <= 65536 and zero-together; line 360 only checks owner < grid; wex4_tools.c line 198 memsets layers*experts*72 into a caller buffer with no capacity argument; wex4.py line 350 has the same gap. Spec line 106 says num_layers is 0 when the file has no expert records, and no reader enforces it. 65536*65536*72 = 309,237,645,312 is correct. Caveat on rating: the readers themselves allocate nothing from the grid (the allocation is in the caller/engine, spec 13.2), so on 64-bit this is an unenforced stated rule plus an unbounded caller allocation, not memory unsafety. The 32-bit wrap claim is reasoning only; I did not run it.
- Fix: In wex4_open after the record loop: `if (h->layers && last_owner < 0) return WEX4_E_EXPERT;` and the same need() in wex4.py Reader after its record loop (both readers must change together). Do NOT require grid == max owner + 1: wex4_convert.py upgrade copies the old WEX grid (line 342) and absent trailing experts are legal. For the size: add a capacity argument to wex4_expert_table (refuse when layers*experts*72 > capacity, compute in uint64_t), and state in spec section 6/13.2 that the engine table is layers*experts*72 bytes, bounded by the header (max 288 GiB) unless a grid cap is added; a cap such as layers*experts <= 2^20 in wex4_parse_header + wex4.py + spec section 4 is the stricter option but is a format rule change. test_wex4.py line 224 needs the new argument.

### S2 (minor): wex4_bp_parse / wex4_bp_decode do not cap decoded themselves: u32 wrap in wex4_bp_plane_bytes for decoded > 2^32 - P, and the chunk loop counter wraps for a plane above 2^32 - chunk

- Where: c/wex4.h wex4_bp_plane_bytes (`(decoded - p + planes - 1u) / planes` in u32), wex4_bp_parse (no `decoded > WEX4_MAX_DECODED` check, unlike wex4_bp_encode), wex4_bp_decode loop `for (first = 0; first < b.n[p]; first += b.chunk, ...)`. Exported as wex4_bp_decode_record in wex4/wex4_tools.c.
- Verification: Reproduced at parse level. rv_bp_parse (reviewer's out/rv_harness.dll, which calls wex4_bp_parse directly, harness.c line 223) on findings/wbp1_decoded_ffffffff_parse_accepts.bin (102,400 B, header 57425031 00000000 ffffffff 08 0f 80 00) returns 0 with n = [0,0,0,0,0,0,0,536870911]; wex4.bp_decode on the same bytes raises FormatError 'WBP1 tables'. Code read: wex4_bp_plane_bytes (wex4.h line 420) computes decoded - p + planes - 1 in u32, which wraps for decoded > 2^32 - planes + p; wex4_bp_parse has no decoded cap while wex4_bp_encode has one (line 541); loop at line 498 uses u32 `first += b.chunk`. Not reachable through a container: wex4_open line 317 refuses rec.decoded > WEX4_MAX_DECODED. Only the exported wex4_bp_decode_record with a caller-supplied decoded > 2^30 is exposed. The decode-returns-0-with-planes-unwritten and loop-wrap consequences are reasoning only (need a ~4 GiB buffer); I did not run them.
- Fix: wex4.h wex4_bp_parse first condition: add `|| decoded > WEX4_MAX_DECODED`. wex4.py bp_decode line 214: add `decoded <= MAX_DECODED` to the first need(). Both together, so the two codecs keep agreeing; no container that opens today is affected (the index already caps decoded at 2^30).

### S3 (minor): WNR3 chunk-size fields (record bytes 16..23) are covered by no level-1 hash: a changed value is accepted with SHA-256 off when every matrix still fits one stream, against fuzzing rule (c) of spec section 9

- Where: c/wex_neural_rans.h wex_nrx_parse / wex_nr2_decode (ident = {model_id, owner, g, word24}; weight_chunk and scale_chunk are not in it), reached from c/wex4.h wex4_decode_record with check_sha = 0. Spec: docs/WEX4-SPEC.md section 9 fuzzing policy (c) "compressed record bytes mutated with the record SHA-256 switched off must be rejected by the codec"; wex4/test_wex4.py test_fuzz does not assert `same == 0` in mode 1.
- Verification: Reproduced. The reviewer's file differs from wex4/out/tiny_nr3_cz.wex4 in exactly one byte, offset 2191381 (record offset 2191360 + 21, scale_chunk 0x200 -> 0x4000). flags 2: status 0 in fast, ref and Python, digest equal to the original; flags 3: -3 / -3 / 'record hash mismatch'. My own mutation scale_chunk -> 256 is also accepted with identical digest; scale_chunk -> 1 and weight_chunk -> 8192/16384 are rejected (-14). So decoded bytes are never wrong; only spec section 9 rule (c) ('must be rejected by the codec') is literally false for these mutations. test_wex4.py line 353 asserts same == 0 only for mode 0, so the test already tolerates it. I did not re-run the 1,608,000-mutation campaign (the 347 count is unverified) and did not check the production container.
- Fix: Spec only: reword section 9 (c) to 'must be rejected by the codec or decode to the identical bytes', and add one sentence in the WNR3 integrity text that the two chunk-size fields are not covered by the level-1 stream hashes (only by the record SHA-256). No code change: making the old WNR3 parser stricter would touch c/ and the engine's accepted set.

### S4 (minor): The guard pages of wex4_fuzz_check only see the end of the file and the end of a max_decoded buffer

- Where: wex4/wex4_tools.c check_impl (`out = guard_alloc(h.max_decoded, guard)`, one buffer for every record) and wex4_fuzz_check (one guarded copy of the whole file). Spec section 9: "Buffers sit against inaccessible pages so that an out-of-bounds access is a crash, not a pass".
- Verification: Confirmed by reading wex4/wex4_tools.c: check_impl line 67 allocates one output buffer of h.max_decoded for all records, and wex4_decode_record (line ~100) is handed file + rec.offset inside the single guarded copy made by wex4_fuzz_check (line 148). guard_alloc places only the END of a buffer against the PAGE_NOACCESS page, so a record with decoded < max_decoded has unguarded slack after its output, and a record that is not the last extent is followed by mapped file bytes. The spec sentence in section 9 line 318 is therefore true only for the last extent and the largest record. This is a test-strength weakness, not a decoder defect; I did not re-run the reviewer's stricter harness campaign, so the 'no fault found' claim is unverified by me.
- Fix: In check_impl, when guard is set: per record, out = guard_alloc(rec.decoded, 1) and stored = guard_alloc(rec.stored, 1) + memcpy from file + rec.offset, decode from that copy, free both after hashing the tensors (move the alloc/free inside the record loop; keep the single max_decoded malloc when guard is 0 so wex4_check speed is unchanged). rec.stored is page-aligned, so the copy ends exactly on the guard page.

Readers agree; text-only gap.

## spec-vs-code

### S1 (major): Expert grid (num_layers x num_experts) is not tied to the expert records: stated rule unenforced in both readers, and a tiny file can demand a 309 GB legacy table

- Where: c/wex4.h wex4_parse_header (line 161: only `layers > 65536 || experts > 65536 || !layers != !experts`) and wex4_open (no check after the record loop); wex4/wex4.py Reader.__init__ line 350 and _validate; wex4/wex4_tools.c wex4_expert_table line 198; spec section 4 (num_layers: "0 when the file has no expert records"), section 6 ("Nothing in the file can make it allocate more than that"), section 13.2 (engine fills a layers*experts WexEntry table)
- Verification: Reproduced with my own script (wex4/review/spec-vs-code/verify/v.py, ref DLL + wex4.py). t_py.wex4 (grid 0x0, no EXPERT record) with header bytes 60..68 set to 3x5 and to 65536x65536, resealed: C wex4_validate 0, Python Reader opens, both full checks 0, same content digest 76beeab372b6 as the baseline. tiny_nr3_cz.wex4 (6x8, 48 expert records) with the grid changed to 7x9: also accepted by both, same digest. Read the code: wex4_parse_header (wex4.h) only tests layers/experts <= 65536 and !layers != !experts; wex4_open only tests owner < grid per EXPERT record; wex4.py line 350 and 445 are the same. wex4_tools.c line 198 memsets layers*experts*72 bytes into a caller buffer sized from the header: 65536*65536*72 = 309,237,645,312 B (recomputed). So the section 4 rule '0 when the file has no expert records' is unenforced in both readers, and section 6 'Nothing in the file can make it allocate more than that' is false for a reader that builds the 13.2 entry table from the header. Caveats: the two readers agree; no memory unsafety in wex4.h itself (wex4_expert_table is a tools function and the caller allocates); the old WEX3 path (c/wex_format.h wex_validate_header) bounds the grid by expected_layers/expected_experts from the engine, which spec 13.2 does not carry over.
- Fix: Both readers, same two checks. (1) Header step (wex4_parse_header and Reader.__init__): refuse when (uint64)layers*experts > 2^24 (record cap; at most one expert record per slot), which bounds the legacy table to 1.2 GB; state it in spec section 4 and in the step-1 list of section 6. (2) After the record loop (wex4_open, Reader._validate): refuse when layers != 0 and last_owner < 0 (no EXPERT record). Checked against the writers: wex4_convert.pack sets the grid only when expert_groups is non-empty, and the upgrade requires at least one present record ('need(present ...)'), so neither breaks; a hand-written wex4.write(..., layers=N) with no expert record would now be refused, which is the stated rule. Also add to spec 13.2 that the engine compares the grid with the model's expected layers/experts before allocating the table.

### S5 (minor): Reader duties stated as normative have no implementation in wex4.h / wex4.py: memory budget, and the blob check of step 3

- Where: spec section 6 last paragraph ("A reader has a memory budget ... refuses a file it cannot afford") and step 3 ("Per blob, when it is first used: read it, check its SHA-256 and zero padding"); c/wex4.h (no budget parameter, no blob function); wex4/wex4_tools.c check_impl lines 73-81 and wex4_decode_record_buf lines 180-187; wex4/wex4.py Reader.blob line 508
- Verification: Confirmed by reading, with one overstatement. Memory budget: neither wex4_parse_header nor wex4.Reader takes a budget; check_impl allocates max_decoded unconditionally (bounded at 2^30 by the header cap). Blob check: wex4.h has no blob-checking function. wex4_tools.c wex4_decode_record_buf (lines 180-187) opens the caller's blob bytes and compares only model.id (FNV-1a computed by wex_nr2_model_open, c/wex_neural_rans.h) with the entry id; no SHA-256, no padding check on that path. - Fix: Add one static inline wex4_check_blob(const Wex4View*, uint32_t i, const unsigned char *bytes_with_padding) to wex4.h (SHA-256, zero padding) and call it in check_impl (replacing lines 73-81) and in wex4_decode_record_buf when check_sha is set. ### S7 (minor): Header is not canonical: required bit 0 (VALUE_EXACT) may be set with no value-exact record

- Where: c/wex4.h wex4_open line 326-327 (one-way check only); wex4/wex4.py line 417; spec section 2 ("Flagged per record and in the header"), section 13.2 (engine sets CANONICAL_ZERO from the header bit)
