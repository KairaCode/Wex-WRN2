# wex4/

**Current.** The WEX4 container outside the engine: reference implementation, converter, C tools, tests, the reviews and the research behind the format. Specification: [docs/WEX4-SPEC.md](../docs/WEX4-SPEC.md); short Italian summary: [docs/reports/wex4-summary-20261111.it.md](../docs/reports/wex4-summary-20261111.it.md). This folder was called `next/` until 2026-11-11.

## What is mirrored and what lives here

The C reader **[`../c/wex4.h`](../c/wex4.h) is the engine-side reader** (`src/colibri/c/wex4.h` in an engine tree). It is the header the engines include, through `deepseek_v4.c` and [`../c/qwen38_wex.h`](../c/qwen38_wex.h). Everything in `wex4/` exists only here:

| File | What it is |
|---|---|
| `wex4.py` | Python reference, standard library only, written independently of `c/wex4.h`: the tests run both on the same bytes and require the same verdict. Command line: `python -I wex4.py info FILE`, `python -I wex4.py verify FILE [--dll out/wex4_tools.dll]` |
| `wex4_convert.py` | `pack` / `unpack` (safetensors to WEX4 and back), `upgrade` / `downgrade` (a WEX1 or WEX3/WNR3 expert container to WEX4 in place and back; the records are not moved). `--names PROFILE` picks the naming profile of the model family ([below](#naming-profiles)) |
| `wex4_store.h` | prototype of the engine loader of spec section 13.2: opens a WEX4 expert container and gives the store the table it keeps today, plus the per-record SHA-256 |
| `wex4_tools.c` | the C side of the tests, loaded through ctypes: validator, codecs, in-process fuzzer. Builds twice, with the reference WNR3 decoder and with the fast one |
| `test_wex4.py` | round trips, C against Python, hostile files, mutation fuzzing, and the check of the conformance vectors |
| `vectors/` | conformance vectors: valid, invalid and legacy files with the verdict a reader must give, the root and content digest of the valid ones and the error class of the others, in `MANIFEST.tsv` ([README](vectors/README.md)) |
| `build_and_test.sh` | builds the two DLLs and the fixtures, then runs `test_wex4.py` |
| `fuzz/` | libFuzzer harnesses for the C reader, the WNR3 decoders (reference against fast), `wex4_verify`, the two engine store files (`c/expert_store_wex.c`, `c/qwen38_wex.h`) and the CUDA WNR3 decoder built for the CPU (against the reference), with custom mutators that re-encode WNR3 records (and, for the store, the older record codecs), seeded with the vectors and with small containers made at run time; `bash wex4/fuzz/run.sh` ([README](fuzz/README.md)) |

The engine side is not here: the loaders are in the engine, shown as patches in [`../integration/`](../integration/README.md) (`engine-wex4-loader-75932c1.patch`, `engine-wex4-first-read-4ba5568.patch`, `engine-q38-wex4-loader-de17198.patch`).

## Run the tests

CPU only, no real model, standard-library Python. On Windows: MSYS2 UCRT64 or MINGW64 `gcc` on `PATH`. On Linux: `export PYTHON=python3`. On macOS: `export PYTHON=python3 CC=gcc-15` (a Homebrew GNU gcc; the script takes the compiler from `CC`, default `gcc`), or Apple clang with Homebrew `libomp` in `WEX_OPENMP` (the header of `build_and_test.sh` shows the line).

```sh
bash wex4/build_and_test.sh            # from the repository root; add --fuzz N to change the mutation count (default 1000)
```

The line before the last checks the conformance vectors; last line on success: `WEX4 prototype: all tests passed`. Everything built goes to `wex4/out/` (git-ignored). The script builds a WEX1 and a WNR3-CZ container from [`../fixtures/v41-tiny`](../fixtures/README.md) and a synthetic one, so it also exercises `c/tools/repack_v4_wex.py`, `c/tools/build_nr3.py` and `c/tools/wex_nr3_tools.c`.

Two decoders are compared on purpose. `c/wex4.h` always calls the reference WNR3 decoder; `wex4_tools.c`, built with `-DWEX4_FAST_NR3`, puts `research/fast-cpu-decode/wex_fast_decode.h` (AVX2 + OpenMP on x86-64, NEON + OpenMP on AArch64; on any other CPU its scalar kernel, still parallel across streams; the script prints which one it built) under that name. The script stops if the two DLLs do not differ at that call site, because a sync of `c/wex4.h` once removed the hook and the comparison then tested the reference against itself.

**What fits.** An EXPERT record is an MXFP4 slab ([WEX4-SPEC](../docs/WEX4-SPEC.md) section 5.5): three matrices, each with a scale tensor (U8 or F8_E8M0, `[rows, cols]`) and a weight tensor (U8 or I8, `[rows, 16 * cols]`), every dimension at most 65,535. The checkpoints above have this form for one expert at a time, so they need no format change. `pack` checks every expert the profile finds:

- An expert with a tensor of another dtype (a float or FP8 expert) stays ordinary tensors (WBP1 or RAW records), is counted in the line `pack` prints, and comes back byte for byte with `unpack` like everything else. Under a `-ct` profile the weight tensor of such an expert is a plain `.weight`, which the profile does not match; when a matrix has no `.weight_packed` but has a `.weight` that is not U8 or I8 (for example an F8_E4M3 weight with a U8 `weight_scale`, an MXFP8 expert), the expert also stays ordinary tensors. A BF16 expert with no scale tensor matches nothing under any profile and stays ordinary tensors too. A `.weight` that is U8 or I8 is taken for the wrong profile and refused as below.
- An expert whose tensors all have MXFP4 dtypes must be a whole slab. If one of the six tensors is missing (a shard was left out, or the profile is the wrong one for this export) or a shape does not fit, `pack` stops with `incomplete expert` or `expert tensor shape`, names the layer and the expert, and writes no file. This is the refusal `pack` had before the profiles.
- If `--experts` makes no expert record at all, `pack` still writes the container and prints a warning on stderr (exit code 0): the usual cause is a wrong or forgotten `--names`. `--names` without `--experts` is refused.

**Limits.**

- The profiles were tested on synthetic fixtures (`fixtures/make_synth_mxfp4.py --names`, 2 layers x 3 experts, hidden 512 x intermediate 256). On 2026-11-15 three of them also round-tripped real tensors: 8 routed experts (2 layers x 4) each of `deepseek-ai/DeepSeek-V4.1-Flash` (`deepseek`), `amd/Qwen3-235B-A22B-Instruct-2507-MXFP4` (`qwen3-moe`) and `amd/MiniMax-M2.1-MXFP4` (`mixtral`), fetched with range requests, through `pack --experts raw|nr3`, both readers and `unpack` ([research/real-experts-20261115](../research/real-experts-20261115/README.md)). On 2026-11-16 `qwen38` converted a whole checkpoint, `amd/Qwen3.5-35B-A3B-MXFP4` (14 shards, 24.6 GB): `pack --experts raw` made 10,240 expert records and kept 0 experts as ordinary tensors, `wex4.py verify` passed and `unpack` gave the 14 files back with their SHA-256 ([research/converter-qwen35-20261116](../research/converter-qwen35-20261116/README.md)). No whole checkpoint of another family was converted, none was packed with WNR3 expert records, and the other twelve profiles have met no real tensor.
- On 2026-11-14 the repository `amd/Auto-Mixed-Precision-Mixtral-8x7B-Instruct-v0.1-Weight-Activation-Mixed-MXFP4-FP8PT-KVFP8` held no safetensors file. The MXFP4 Mixtral of the `mixtral` row, found on 2026-11-15, is another repository of the same publisher, and a mixed one.
- The search of 2026-11-15 was the Hugging Face model search for `mxfp4` (it returns at most 1,000 models, sorted by downloads) and the same search limited to the publishers `amd`, `amd-quark`, `RedHatAI`, `intel-ai`, `Intel`, `INCModel`, `INCModel2`, `INCModel3`, `olka-fi`, `nm-testing`, `inference-optimization` and `vllm-project`. For 41 of the checkpoints it found, the file list was read, and for 37 of them the index; the header of one or two shards was read in 27 (29 shards). The others were not opened, and a checkpoint whose name does not contain MXFP4 was not found this way.
- The engines of this repository read DeepSeek V4 and V4.1 and Qwen3.8 only. For the other families the profiles serve the container tools (`pack`, `unpack`, `upgrade`, `verify`), not an engine. The tools that write a WEX1 container (`c/tools/repack_v4_wex.py`, `c/tools/repack_q38_mxfp4_wex.py`) know the DeepSeek and Qwen3.8 names only, so for the other families the way in is `pack --experts`.

The test is `test_profiles` in `test_wex4.py`. For every profile it packs the fixture with RAW and with WNR3 expert records, checks the file with both readers, compares each decoded record with the slab of the WEX1 container of the same experts, and unpacks to the same bytes. It upgrades a WEX1 and a WNR3 container with the profile's names, reads every tensor of the fixture back by name, and downgrades to the same bytes. It also packs a mixed checkpoint (a first layer without experts, an MXFP4 layer, a float layer), a fixture under every other profile's names, and names that only look like experts. It checks the refusals (an MXFP4 expert with a missing file, a missing tensor or a wrong shape; the `deepseek-quark` fixture under the `deepseek` profile; each `-ct` fixture under the profile with the same names and `.weight`, and the `qwen3-moe` fixture under `qwen3-moe-ct`, where only the scale tensors match) and, through the command line, the warning and the refusal of `--names` without `--experts`.

### Matrix roles

Which of the three matrices is the gate, the down and the up matrix matters to an engine that reads a slab, not to the converter: the slab order is by name, and the round trip is byte for byte either way. For the profiles with `gate_proj`, `down_proj`, `up_proj` the names say it. A header alone cannot always tell: in the Mistral Large 4 header the three matrices have the same shape (weight `[6144, 3072]`, scale `[6144, 192]`). For the profiles with w1, w2, w3 it was read on 2026-11-15 in the model code: Hugging Face transformers on GitHub at commit `3a134bc37f7c22c801b618e289b0255425f22647` (`main` of 2026-11-14, written 3a134bc3 below), and the model code in the checkpoints' own repositories where they have one. The answer is the same for all: **w1 is the gate, w2 the down and w3 the up matrix**. So the slab order w1, w2, w3 is gate, down, up, the order of [WNR3-SPEC](../docs/WNR3-SPEC.md) section 1 (m = 0 gate w1, 1 down w2, 2 up w3) and of the `gate_proj`, `down_proj`, `up_proj` profiles.

How transformers 3a134bc3 reads these names: at load time `src/transformers/conversion_mapping.py` stacks the w1 and the w3 tensors of the experts into one `gate_up_proj`, w1 first (`Concatenate` keeps the order of the source patterns, `src/transformers/core_model_loading.py` lines 205-219), and the w2 tensors into `down_proj`. The forward of the experts multiplies by `gate_up_proj`, splits the result in two with `chunk(2)`, takes the first half as the gate and the second as the up projection, and applies `down_proj` last.
