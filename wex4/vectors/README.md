# WEX4 conformance vectors

Small WEX4 files with the verdict a conforming reader must give ([WEX4-SPEC](../../docs/WEX4-SPEC.md), section 17). Use them to test a reader or a writer written from the specification, in any language.

| Folder | Files | What a reader must do |
|---|---|---|
| `valid/` | 15 | open the file, verify every hash, decode every record, and report the root given in the manifest. The WNR3 records need a WNR3 decoder: [WNR3-SPEC](../../docs/WNR3-SPEC.md), whose section 12 says what else to read ([WNR2-REFERENCE](../../docs/WNR2-REFERENCE.md) sections 6 and 7) and lists the checks of a decoder with the vector of each |
| `invalid/` | 113 | refuse the file, without reading or writing out of bounds, allocating without limit or hanging |
| `legacy/` | 1 | a WEX3 file with WNR3 records: not WEX4, so a WEX4 reader refuses it (wrong magic); it is the input of the upgrade test below |
| `../review/security-c/findings/` | 10 (its `.wex4` files; the two `.bin` files there are WBP1 records on their own, not containers, and have no row) | the files of the 2026-11-11 security review, which stay in the review folder; their current verdicts are listed too |

`MANIFEST.tsv` has one row per file, tab-separated:

| Column | Meaning |
|---|---|
| `path` | relative to this folder |
| `verdict` | `accept` or `reject` |
| `class` | for a rejected file, the status the C reader (`c/wex4.h`, `wex4_check` with hashes on) returns, as its `WEX4_E_*` name. It is informative (WEX4-SPEC section 17): another reader only has to refuse the file, and the class it reports is its own. The class says which rule the file breaks first in the C reader's order |
| `root` | for an accepted file, the root: SHA-256 of bytes [0, 4064) of the header page, also stored at byte 4064 |
| `sha256` | of the whole file, so that a damaged copy of a vector is not mistaken for a reader bug |
| `upgrade_of` | for `valid/tiny2-cz-upgraded.wex4`: `legacy/tiny2-cz.wex3`. The in-place upgrade (`wex4/wex4_convert.py upgrade`) of that file must give this file byte for byte; a converter written elsewhere can be checked the same way |
| `content` | for an accepted file, the content digest of WEX4-SPEC section 5 (SHA-256 over the fields and the decoded bytes of every tensor); `-` for a refused one. A reader that decodes every record checks its bytes with it, not only its verdict: the stream hashes of WNR3 and WBP1 cover the coded symbols, before the inverse of the ceil form and of the rotation, so a decoder that gets those wrong passes every hash. The column was added on 2026-11-15, as the last one: a reader of the six-column form reads the other columns as before |

What the valid files cover:

- `generic.wex4`: written from scratch, index right after the header page; 12 tensors (one record holding several tensors, a split tensor, a zero-size tensor, a scalar, an opaque dtype), RAW records and WBP1 records (codec 6), free-form metadata.
- `generic-index-last.wex4`: the same content with the index after the records; same content digest, different root.
- `tiny2-cz-upgraded.wex4`: the in-place upgrade of a WNR3 container with canonical zero (the layout of the DeepSeek V4.1 production file), 2 experts, with the WNM2 model blob and the old header page and entry table kept as blobs.
- `tiny-raw-upgraded.wex4`: the in-place upgrade of a WEX1 container of RAW records (the layout of the Qwen3.8 production files), 6 layers x 8 experts.
- `minor-version-9.wex4`, `unknown-optional-feature-bits.wex4`, `bytes-in-the-reserved-header-area.wex4`: forward-compatible changes of `generic.wex4` that a reader must still accept (section 10).
- `opaque-tensor-of-0-bytes-with-shape-3-x-3.wex4`, `opaque-tensor-of-0-bytes-of-rank-0.wex4`: a zero-size tensor is one with `nbytes = 0`; for an opaque dtype it needs no 0 dimension (WEX4-SPEC 5.3).
- `tensor-shape-0-x-2-32-x-2-32.wex4`, `tensor-shape-2-32-x-0-x-2-32.wex4`: zero-size F32 tensors whose shape is multiplied from the first dimension to the last, so that no multiplication overflows (WEX4-SPEC 5.3). Their pair `invalid/tensor-shape-2-32-x-2-32-x-0.wex4` overflows before it reaches its 0 and is refused, as is the review file `a2_005.wex4`.
- `wbp1-records-of-4-and-8-planes.wex4`: WBP1 records of 4 and 8 planes, with the rotation (F32, F64) and without it (I32, I64), and one of 1 plane; rANS-coded and raw planes; the byte 255 in rANS-coded planes; `chunk_log2 = 12`.
- `wbp1-record-sizes-not-a-multiple-of-the-planes.wex4`: WBP1 records of 5,001 B in 2 planes, 10,001 B in 4 and 20,003 B in 8, `chunk_log2 = 11`, with a raw plane in two of them.
- `wnr3-ceil-form-chunk-pairs-and-anchors.wex4`: 4 WNR3 records without and with the ceil form, one with canonical zero and the ceil form, chunk pairs 2048:512, 512:256, 4096:1024 and 16384:16384, scale 255 in the scale streams, and a record whose anchors are not those of rule g: it decodes to the same slab as another record of the file ([WNR3-SPEC](../../docs/WNR3-SPEC.md), erratum 14 and section 12).
- `wnr3-one-expert.wex4`: one small WNR3 record in ceil form, without canonical zero, under its own model; the base of most of the refused WNR3 files below.

The invalid files are a valid file with one thing changed each, the header and index hashes recomputed so that the change reaches the validators (except where the file name says the hash was left alone). Their names say what was changed; `wex4/test_wex4.py` builds them.

- 71 are made from `generic.wex4` (`test_hostile`): wrong magic, major version 5, unknown required feature, sizes and offsets past the end or overflowing, overlapping records and tensors, a decompression bomb, duplicate or invalid names (also a UTF-8 surrogate and an overlong form), a truncated file, appended bytes, a non-zero byte in the index padding, a bit flipped in the index or in a record with the hash left alone, and so on. Three of them change bytes inside a record and recompute that record's SHA-256, so that the file passes every check of the index and is refused by the record decoder (`WEX4_E_DATA`): a non-zero byte in the padding of a RAW record, and a WBP1 record damaged in its header or in a stream.
- 25 are made from `tiny2-cz-upgraded.wex4` (`test_hostile_experts`), the only base with blobs, an expert grid and WNR3 records before 2026-11-15: blob entries and blob bytes (`WEX4_E_BLOB`, and a bit flipped in the model blob; since 2026-11-22 also a bit flipped in the old header page and a non-zero padding byte after the old entry table, the two blobs the upgrade keeps and no record uses), WNR3 records without their model blob or their flags, owners outside the grid or out of order, expert tensors of the wrong rank or dtype, and three files whose WNR3 data disagrees with the index or is damaged under a recomputed hash (`WEX4_E_DATA`).
- 17 are made by `test_spec_cases` (16 on 2026-11-15, one on 2026-11-22), each from a small file of its own: the shape `[2^32, 2^32, 0]`; a WBP1 record and a WNR3 record with one page of zeros too many; a blob whose offset is not a multiple of 4096; an expert weight tensor with other rows than its scale tensor, and one of 65,536 columns; eight WNR3 records that break one rule of WNR3-SPEC each (magic, reserved flag bit, model id, weight chunk 256, payload sizes, padding, a nibble 8 under canonical zero, a ceil-form block of maximum 5 at coded scale 0); a WNM2 blob with a table that is not increasing (in a context no symbol is coded in, so a decoder that does not check the tables decodes the record), and the same blob as a second WNM2 blob that no record uses, next to the good model of the record; and a WNR3 record of 4,096 B whose three matrices need 792 streams, under the minimum size of WEX4-SPEC 5.2 (no record of that size can hold its streams, so a reader that decodes refuses it also without that check, with another class). For the WNR3 ones the record is encoded as it is written, by a WNR3 encoder in Python, so that the file breaks that one rule and no other. That encoder takes anchors, flags, chunks and model id as it is given them; on the 3 records that the C encoder can also write (chunk pairs 2048:512, 512:256 and 4096:1024; plain, ceil form, canonical zero with the ceil form) its bytes are the C encoder's, and no other record was compared.

A reader that validates the index but does not decode records (as `c/tools/wex4_verify.c` does) cannot refuse the sixteen `WEX4_E_DATA` files, whose index, hashes and blobs are valid and which the record decoder refuses. `wex4_verify` passes those sixteen and the 15 valid files, and refuses the other 97 invalid files (run once on 2026-11-22, Windows, gcc 16.2). Until 2026-11-21 it did not open the WNM2 blobs and also passed `wnm2-blob-id-differs-from-its-model.wex4` and `wnm2-blob-with-a-table-that-is-not-increasing.wex4`, refused when the model blob is loaded (WEX4-SPEC section 6, step 3); since 2026-11-22 it opens every WNM2 blob, as a whole-file check must. The sixteen are in the set for readers that decode, which must return no byte of those records.

**Blobs that no record uses.** Three invalid files are damaged only in a blob that no record names: `unused-blob-of-kind-16-bit-flip-hash-not-fixed.wex4` (`WEX4_E_HASH`), `non-zero-byte-in-the-padding-of-an-unused-blob-of-kind-17.wex4` and `unused-wnm2-blob-with-a-table-that-is-not-increasing.wex4` (`WEX4_E_BLOB`), added on 2026-11-22 ([issue 57](https://github.com/KairaCode/Wex-WRN2/issues/57)). Their verdict in the manifest is that of a whole-file check, the kind of check that prints a root to pin, which checks every blob (WEX4-SPEC section 6, step 3). An engine store checks a blob only when it first uses it and may open these three files: the reference store `wex4/wex4_store.h` opens them and reads every record (`test_wex4.py` checks this), and so, by code reading, does the qwen38 store `c/qwen38_wex.h`. A reader that is not a whole-file check, and says so, may treat them as accepted.

One case is left out on purpose: a record that is neither EXPERT nor VALUE_EXACT with a codec id the reader does not know. Such a file opens (WEX4-SPEC section 10, rule 6) and only that record cannot be decoded, so it is neither a file to refuse nor one whose every record decodes. `test_spec_cases` checks, outside the manifest, that both readers open such a file also when the record names a blob, and refuse only to decode that record (WEX4-SPEC 5.2); the Go reader gave the same answer (exit code 3) on three such files on 2026-11-15, one run.

## How the vectors are checked here

`bash wex4/build_and_test.sh` (and `bash scripts/check_all.sh`) ends with a check of every row: the file hash, the verdict and class of the C reader with the fast WNR3 decoder, the verdict of the C reader with the reference WNR3 decoder, the Python reader's verdict, the root, the content digest, and the upgrade. The digest is compared three ways: the C reader with the fast and with the reference WNR3 decoder, and the Python reader. The Python reader decodes RAW and WBP1 records itself and WNR3 records through the C library (WEX4-SPEC section 9), so on the 13 accepted files without a WNR3 record it is read a second time without the library, and on the 3 with WNR3 records its digest comes from the C decoders. The vectors are written by `wex4/test_wex4.py` itself, from the same files its tests build; after a change of the format, a maintainer runs `bash wex4/build_and_test.sh --write-vectors "$PWD/wex4/vectors"` and commits the new files with the specification change. A vector whose verdict changes is a format change. On 2026-11-15 a second run of that command gave the 136 rows byte for byte again (same machine, same day, Python 3.14 on Windows; other Python versions were not tried).

The Go reader checks the same rows in CI: [impl/go-wex4/](../../impl/go-wex4/README.md), written in Go from the specification pages and not from the two readers above (its content digest included: the one of the Go writer, see that README's "Limits"). `bash impl/go-wex4/run.sh` gives the manifest's verdict, class, root and content digest on all 136 rows (2026-11-15; it needs Go and is not part of `scripts/check_all.sh`). The 24 files of 2026-11-15 hold, among other things, the gaps that part D of its [SPEC-NOTES.md](../../impl/go-wex4/SPEC-NOTES.md) and finding 17 of the [spec review](../../research/spec-review-20261114/README.md) listed: before them a reader could read symbol 255 of a rANS-coded plane from the wrong CDF entry, skip the inverse of the ceil form, undo the rotation for 2 planes only, accept a WBP1 record with a page of zeros too many or refuse an opaque tensor of 0 bytes without a 0 dimension, and still pass all 112 rows.

The Rust reader of [impl/rust-wex4/](../../impl/rust-wex4/README.md), written the same way, checks them in CI too: `bash impl/rust-wex4/run.sh` gives the manifest's verdict, class, root and content digest on all 136 rows (2026-11-16; on the 139 rows of 2026-11-22, one run; on the 112 rows of 2026-11-14 when it was written; it needs cargo and is not part of `scripts/check_all.sh`). Part C of its [SPEC-NOTES.md](../../impl/rust-wex4/SPEC-NOTES.md) adds four gaps of the index: no empty index, no blob of kind 18, no file above 4 GiB, and the unknown codec left out above. Its part E lists the classes on which the readers differ on files outside the manifest (the verdicts agree).

Size: 129 files in this folder besides `MANIFEST.tsv` and this README (the manifest has 139 rows: these and the 10 review files), 16,386,049 B; the 24 files of 2026-11-15 added 1,282,048 B, the 3 of 2026-11-22 339,968 B (the packed size below was not measured again). Most invalid files are near copies of a valid file, so git packs them well. Measured with git 2.56.1 on 2026-11-15: `git pack-objects --no-reuse-delta --no-reuse-object` with `pack.threads=1`, on the blobs of the folder without this README, so that the deltas are recomputed the same way each time (two runs, same size): 888,544 B, against 746,070 B before the 24 files. With one thread per CPU (8 here) git finds fewer deltas, and the size differs from run to run; the size in another clone depends on how it was packed.
