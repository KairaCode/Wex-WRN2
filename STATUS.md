## Planned

Nothing on the containers is planned. Decided on 2026-11-13: the Qwen3.8 root stays recorded and not pinned, after its A/B (decode +0.5% to -9.1% per request, median -4.8%; [docs/BENCHMARKS.md](docs/BENCHMARKS.md), "Qwen3.8-Flash-Next MXFP4"). That A/B set only `COLI_WEX_ROOT`, which in the qwen38 engine is a check at open; it did **not** measure the SHA-256 of each record at its first read, which needs `COLI_WEX_VERIFY=1`. Still open:
- the cost of `COLI_WEX_VERIFY=1` on Qwen3.8 decode, to be measured before it is turned on;
- `wex4.py verify` on the real Qwen3.8 files.

Decided on 2026-11-21, by analysis only: neither container moves to WNR4 ([docs/WNR4-SPEC.md](docs/WNR4-SPEC.md), DRAFT 0.1), a research draft of a successor of WNR3 with kinds MX (MXFP4), NV (NVFP4), GG (the Q2_0 and IQ4_NL slices of GGUF experts) and, since 2026-11-22, I4 (int4-g64 experts), to which WEX4 assigns codec 8 as a draft. No production container holds a WNR4 record and no engine reads one; no engine code was written. On Qwen3.8 the RAM slots WNR4 would free (+14%) are worth only -0.6 to -4.8% of step time in a replay of a recorded expert trace, below the A/B's minimum detectable effect of 7.6%, so the RAW container stays; on V4.1 the only lever is a faster decode of an exposed miss at G = 32, estimated at +1.5 to +3% tok/s, inside the ±3% run noise. The measurements and what would reopen it: [docs/reports/wnr4-research-20261121.md](docs/reports/wnr4-research-20261121.md), sections 7 and 8.

## In the engine, switched off or not measured

These changes reached the engine's main branch with the opt-integ-20261111 merge (2026-11-11) and the rd2-integ-20261112 merge (2026-11-13); the parts under `c/` are in this repository. They are built and tested on CPU and fake-CUDA, and reviewed. The switches stay off by default until a GPU A/B shows a gain.
- **WEX4 first-read SHA-256 off the serial path.** A demand batch hashes its due records in parallel. A record that fails its hash is refused for the rest of the process. Whole and striped reads are tracked separately. Since 2026-11-13 the GPU-direct fill also hashes a RAM record-cache hit before it serves it, as the batch path does (a record that passed costs one seen-bit load, a failed one leaves the cache).
- **Hash pool** (`V4_WEX_SHA_ASYNC=1`). Host reads and prefetch batches are hashed on 4 threads while they decode; a record is published only after its hash passes. **Measured neutral: start to first token -0.2%, decode +0.5%, so it stays off.**
- **Integrity lane.** `tools/wex4_verify` checks a WEX4 file and prints its root (used on the Qwen3.8 copies on 2026-11-13). qwen38 can hash each WEX4 record at its first read with `COLI_WEX_VERIFY=1` (default 0, not set in the profile). Under a pinned `COLI_WEX_ROOT` a container that is not WEX4 is refused: V4 falls back to the safetensors, qwen38 stops (this refusal is active in `v41gpu`, whose root is pinned).
- **Demand reads striped over the primary and the mirror** (`V4_WEX_STRIPE=1`, default off). Each record is split at a 4096-aligned cut weighted like `COLI_WEX_WEIGHTS`, and the first-read hash still covers every byte. Qwen3.8 has the same switch for lone decode misses. **Measured on V4.1: -8.72% ± 2.66% (ABBA, 3 prompts, identical tokens), so it stays off.** The extra requests queue behind prefetch reads; the lever is giving demand reads priority, not splitting them. (`V4_WEX_SUBREADS`, which is on, splits a record into overlapped reads in the same queue instead.)
- **Pre-Ampere fallback in `wex_cuda.cuh`.** Below sm_80, `cp.async` becomes a plain load and store, so the WNR3 GPU decoder builds for Pascal and Turing. It has not run on such a GPU yet. Its code path (built with `__CUDA_ARCH__` 750) runs on the CPU in the emulation of `wex4/fuzz/fuzz_wnr3_cuda.cpp` since 2026-11-15, with the verdicts and the bytes of the CPU reference; that is not a run on a GPU. The same day it also ran on an Ampere GPU (RTX 3070), as PTX for `sm_75` that clang wrote and the driver compiled (`wex4/fuzz/run.sh --gpu`), with the same verdicts and bytes; that is not nvcc's build, and not a Pascal or Turing GPU. On 2026-11-16 the helper as nvcc builds it, for `sm_86` (CUDA 13.5), passed `c/tests/test_wex_nr3_gpu.cu` on that GPU, also on 17 records of the published V4.1 container ([research/cuda-real-20261116](research/cuda-real-20261116/README.md)); that build has no code below `sm_80`, so the fallback is still not run by nvcc's build.
